# AI 任务恢复与并发上限

本次修复仅修改源码，未部署或连接真实摄像头。

## 配置与发布影响

```toml
[Server.AI]
MaxTasks = 32
```

- 默认最多容纳 32 个任务；`0` 同样使用默认 32，负数显式取消上限，正数为指定上限。修改后重启生效。
- Go 启动 Python 时传递 `--max-tasks`；独立启动 Python 时也需设置相同值，未设置默认 32。
- **Go 程序和 analysis Python 代码必须配套升级**。旧 Python 不支持新的启动参数及终态重建语义。RPC 消息结构未修改，不涉及数据库迁移。
- 如果已有超过 32 路启用 AI，升级重启前应按实际资源调整上限。否则重启后仅恢复到上限，其余通道保留启用配置、等待空位。32 是保护默认值，不是硬件承载能力或推理吞吐承诺。
- 已运行的正常任务不会因为本轮同步发现超限而被主动裁减。新任务按通道 ID 顺序尝试启动；不轮换抢占，不保证等待任务的公平调度。
- 手动启用达到上限会返回错误，未成功启动不会将新通道保存为启用。后台恢复达到上限则保持数据库配置并记录等待日志。现有页面的“启用”表示期望配置，不代表运行状态；实际运行情况以 Python GetStatus 和服务日志为准。

## 恢复与停止规则

1. Go 启动 30 秒后首次同步，此后每轮结束等待 5 分钟再同步。离线通道停止分析，在线且启用的通道恢复；失败任务在后续同步重试。
2. 使用唯一 ID 游标每批扫描 200 个通道，移除原先 999 条限制。获取完整期望集合和成功且 ready 的 GetStatus 后才操作任务；任一分页失败、状态查询失败或模型未就绪时不启停。
3. GetStatus 是运行状态来源，不再依赖 Go 内存缓存或停止回调。Python 单独重启后，即便 Go 没重启，也会补建缺失任务；迟到回调不会清除新任务状态。
4. 执行启停前重读数据库，手动开关的 RPC 与配置提交、配置重载和单步同步共用锁，避免过期快照重新启用用户已关闭的任务。
5. Python 对正常任务的重复 StartCamera 幂等；对 error/stopped/stopping 任务，先尝试停止旧任务，确认分析线程、采集线程退出和 FFmpeg 回收后才重建。未完成停止仍占用容量，不创建重叠任务。停止不存在的任务视为成功；Go 必须收到成功响应才报告停止成功。
6. 推理异常计入重试预算，成功推理后清零；达到预算进入 error。分析线程退出时停止采集，确认任务停止后释放该通道的背景图缓存。GetStatus 的 active_streams 只计算 running/initializing，不把错误任务算作活跃。
7. GetStatus 最长 10 秒，单次 Start/Stop 最长 15 秒，整轮同步最长 5 分钟。容量或连接故障会中止本轮启动，避免大量请求逐个超时；下轮继续对账。因此恢复是最终收敛，不保证严格在 5 分钟内全部完成。

停止中的 ffprobe 可能仍在其 15 秒探测超时内；分析线程也可能尚在推理。此时停止接口会报告未完成，保留任务并等待重试，不假报释放。永久卡死的线程不会强制终止，需要运维检查或重启 AI 服务。

## 本地检查与人工验收

已执行针对性 Go AI 测试及 race 检查，覆盖 1001 通道完整扫描、Python 空状态模拟重启、终态恢复、离线/禁用/删除清理、分页/RPC/就绪状态失败、停止未确认、容量等待恢复、同步期间关闭及重载使用旧配置。app/conf/ipc/rpc 相关包编译通过。

Python `test_runtime.py` 共 9 项测试通过，覆盖 40 个并发启动请求中只允许 32 个、旧任务停止未完成禁止重建、幂等停止、活跃状态计数、分析/采集线程停止边界、连续推理错误进入终态，以及此前采集重试和健康检查回归。

以上使用本地 SQLite 和模拟 RPC/推理边界，未进行真实模型、摄像头或硬件负载验收。发布后人工重点检查：

1. 单独重启 Python，确认在线且启用的通道在后续同步恢复；关闭的通道保持停止。
2. 断开并恢复一路摄像头，确认任务失败、离线停止及上线恢复，且同一路没有重复 FFmpeg。
3. 按机器负载验证所设上限，检查达到上限的提示，以及释放容量后原已启用任务的恢复。
