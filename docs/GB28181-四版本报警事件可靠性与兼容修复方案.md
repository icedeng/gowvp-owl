# GB28181 四版本报警事件可靠性与兼容修复方案

日期：2026-11-11。状态：第一批恢复可用性已实施并上线，历史恢复 95 条，已验证 18 条真实新报警入库；后续批次仍为方案，不表示已全部实施或所有厂商均通过真机验收。

第一批交付、检查、边界和回滚详见 `deploy/releases/alarmfix-20261111.md`。

## 1. 目标与范围

覆盖 GB/T 28181 的 2011、2014、2016、2022 设备报警，以及直连和公网网关接入。复用现有 `gb_task_states`、报警收件箱、事件中心 `source_key` 唯一约束、手工订阅持久化和续订线程，不新增消息中间件。

完成目标：合法报警持久接收后不依赖设备重传即可进入事件中心；设备重传不重复创建事件；双方式上报按明确规则关联；报警订阅与国标布防状态可见；厂商兼容只作用于接收入口。

范围不包括 AI 检测算法、摄像头检测区域/灵敏度、录像和媒体传输协议改造。此次海康现场已证明本地检测正常，不调整检测配置。

## 2. 问题与优先级

| 优先级 | 问题 | 影响与处理 |
|---|---|---|
| P0 | 旧通知配置为空导致 panic | 四版本共用路径；已有本地空值保护，合入第一批修复并发布 |
| P0 | SIP 确认后、业务提交前异常，后台只等待设备重传 | 四版本可能有已接收但不可见的报警；拆分接收与后续副作用，支持独立入库重试 |
| P1 | MESSAGE/NOTIFY 的同一次上报不能关联 | 可能重复创建事件、重复业务通知；保留报文身份，增加业务事件身份 |
| P1 | 订阅成功不代表设备已国标布防 | 部分设备无报警；增加持久接收策略、独立布防状态和恢复流程 |
| P1 | 接收规则对厂商变体仍有限制 | 按版本和设备兼容档案规范化，不全局关闭校验 |
| P2 | 页面自动续订提示与实现不符、报警分类不充分 | 修正文案，展示报警类型、处理状态和失败原因 |

## 3. 可靠接收与事件入库

### 3.1 接收事实独立持久化

现有 `BusinessCommittedAt` 同时承担非回调副作用门禁，而事件入库又在该门禁之后，导致通知函数异常可以阻断事件中心。

新的接收顺序：

1. 校验 SIP 认证身份、设备/通道归属、订阅对话（NOTIFY）、XML 与报警字段。
2. 在现有设备注册代次门禁内，将已接纳的报警写入持久收件箱。
3. 持久化成功后，按协议版本完成 SIP 确认和业务应答。
4. 唤醒事件入库线程；后续通知和转发不再作为事件入库的前置条件。

新版收件箱 payload 增加格式版本、合法接纳时间、内部设备/通道 ID 快照、国标 ID、来源入口快照、投递 ID、原始 XML/规范化字段以及独立的事件写入进度。原始报文不保存 SIP 鉴权头。

事件入库只消费已持久化、明确标记为合法接纳的记录。不能简单删除旧代码的 `BusinessCommittedAt` 检查，把所有历史记录无条件当作已通过认证。

### 3.2 后台恢复与事务边界

- 应用启动、收件箱唤醒、定时扫描均处理待入库记录，复用现有退避机制。
- 事件中心使用稳定 `source_key` 和数据库唯一约束，允许至少一次投递；即使事件写入后、收件箱状态更新前崩溃，重试也返回已有事件。
- 数据库不可用时保留任务并退避，恢复后自动继续，不要求摄像头重传。
- 有限期重试仍失败的记录进入可查询、可重放的失败队列；待处理/失败报警不按普通已完成记录静默清理。
- 新事件与业务通知任务在同一数据库事务内提交；发送网络通知不占用数据库事务。
- 事务外 webhook 不能承诺恰好一次，携带稳定事件 ID 供接收方幂等；已成功投递的任务不重复生成。

### 3.3 与设备代次及转发隔离

重新注册或网关重连不会撤销过去已经合法接收的报警，因此历史事件入库不依赖当前连接代次。

涉及新 SIP 请求、上级转发、订阅发布和设备运行态修改的操作，继续校验对应注册/订阅代次及授权。为每类副作用保存独立进度，避免入库恢复时自动重放所有网络操作。

设备已删除或同一国标编码被重新建档时，不将历史报警归入新建设备；按内部 ID 快照和现有历史保留规则处理，无法映射的记录进入明确的失败状态。

## 4. 分开处理报文重传与业务重复

### 4.1 保留投递身份

保留现有报文级 `DeliveryID`，继续用于重复报文确认、收件箱与 receipt。每个 MESSAGE/NOTIFY 都独立完成必要的协议应答，不能因业务事件已存在而漏回确认。

### 4.2 增加业务事件身份

事件中心的 `source_key` 使用独立业务键；新增键带算法版本，既有键和 receipt 不直接改写。

| 情况 | 处理规则 |
|---|---|
| 已验证厂商提供稳定事件 ID | 在内部设备/通道及报警阶段范围内使用该 ID；类型、开始/结束含义冲突时不合并 |
| 同一投递重试 | 复用原业务事件；重启后仍由持久映射和数据库唯一约束保证幂等 |
| 无事件 ID，MESSAGE/NOTIFY 双报 | 仅对已确认固件启用跨方式关联；通道、方式、类型、进入/离开等阶段、设备时间及其他有效字段一致，且接收时间接近时尝试一对一配对 |
| 多个候选、时间精度不足、字段冲突 | 不自动合并，保留记录并标记可能重复 |
| 同一种方法、不同 SN、无稳定事件 ID | 默认视作新上报；不能仅凭同一秒就合并 |

跨方式关联窗口按设备档案配置，现场双报可先以 3 秒作为候选窗口再验证；窗口只用于寻找对应报文，不是将窗口内所有报警聚成一条。持久关联必须在数据库事务/锁保护下完成，不能只依赖单进程内存。

对不同 XML 字段顺序、空白及合法时间表达，先规范化再比较；保留完整原始报文。普通文本内容及未知有效扩展不能随意丢弃后再判断等价。

没有设备事件 ID 且时间仅精确到秒时，无法保证业务意义上的绝对去重，默认优先避免吞掉真实事件。

## 5. 已留存报警的恢复

针对本次目标设备的异常记录执行一次受控恢复，不全库更新提交标志：

1. 导出备份，按内部设备、报警时间范围、旧格式及异常状态筛选，输出预览清单。
2. 校验记录身份、通道归属与格式。旧记录缺少完整接纳快照，不自动作为新版任务批量升级。
3. 生成报文与业务事件关联预览，列出可确认重复、可能重复、独立事件和无法恢复项；不能把报文数量直接作为事件数量。
4. 经核对的记录通过专用历史恢复入口写入事件中心，附恢复来源与原投递 ID，使用持久幂等键，支持重复运行。
5. 历史恢复默认不重新触发实时 webhook、上级通知、声音或其他实时联动。
6. 核对成功数、已有数、失败数；未完成项保留证据与失败原因，不删除或伪造完成状态。

该流程只恢复业务事件，不绕过旧注册代次门禁去执行已失效连接的副作用。

## 6. 订阅与国标布防管理

### 6.1 持久接收策略

在设备档案中增加报警接收策略，复用现有可扩展字段：

- 接收报警：启用/停用。
- 接收方式：主动上报、订阅、主动上报与订阅并用。
- 订阅目标、有效期与过滤条件：复用现有参数和持久意图。
- 国标布防策略：手动管理、由平台管理；平台管理需记录命令目标及策略归属。
- 厂商兼容档案与去重策略：独立于设备声明/有效协议版本。

现有设备不因升级被批量布防或新增订阅；已有手工订阅继续保留和自动续订。未由平台接管的设备主动报警仍按原接收规则处理，不能新增默认关闭开关将其拦截。

### 6.2 启用、恢复与关闭

平台管理模式执行：设备在线 → 按已确认设备能力下发布防 → 确认业务结果 → 建立所需订阅 → 持续续订并记录结果。订阅建立失败时展示部分成功；已经收到的合法主动报警照常处理。

不能仅因厂商名称为海康就批量下发命令；对本次已实测 `SetGuard=OK` 的具体设备可采用已确认档案，其他型号/固件先查询或验证。

重新注册、设备重启、服务恢复后，对照持久期望状态重新协调；不在每次心跳上重复布防。查询不到布防状态时，显示未确认，并按已验证命令的幂等能力决定是否重试。超时不能等同于设备明确拒绝。

关闭接收策略时，取消对应平台管理的订阅，不停用其他手工/上级共享订阅。仅当平台明确拥有该布防状态、无其他接收者依赖且关闭策略明确要求撤防时发送 `ResetGuard`；不能盲目撤销用户手动布防。

### 6.3 页面表达

设备运维页提供简单的“报警接收”设置，现有事件订阅表单保留为高级配置，二者使用同一份持久意图，避免重复管理同一订阅。

分别展示：接收期望状态、国标布防确认状态、订阅状态、下次续订时间、最近收到报警、待入库/失败数量及最近错误。创建订阅不显示成“报警链路已验证”，只有实际收到报警并入库后才展示成功证据。

修正“手工订阅需在到期前续订”为“创建成功后由服务端自动续订”；设备拒绝、恢复中和部分成功分别显示，不统一提示成功。事件列表展示报警方式、具体类型和进入/离开等阶段，避免只看到 `gb_alarm_5`。

## 7. 四版本与厂商兼容边界

| 项目 | 解决策略 |
|---|---|
| 2011/2014 字段乱序 | 将已知字段顺序兼容补到接收入口；单例、重复项、必选项和值域继续验证 |
| 2016 文本与结构化 Info 顺序 | 已知结构唯一且无冲突时在内部规范化；不因文本 Info 在前而丢失报警 |
| 2022 沿用文本 Info | 通过设备兼容档案将其识别为旧式文本扩展，内部转换/保留；标准输出使用目标版本格式 |
| 顶层 AlarmType 等已知非标准位置 | 仅按已验证档案接纳并归一到类型字段；标准位置同时出现且冲突、重复时拒绝，禁止覆盖取值 |
| 2011/2014 固件携带后续版类型扩展 | 仅在明确档案下保留可识别元数据，不据此升级协议或开放新能力；转发按目标版本裁剪 |
| 2022 NOTIFY 缺少 expires | 仅在显式兼容档案下沿用已建立对话的剩余有效期；不得延长、复活或创建未知订阅 |
| 非标准 Event 头 | 仅允许设备档案中的明确别名，并仍匹配原订阅事件和对话；未知事件不直接接纳 |
| 未知结构化扩展 | 保留可脱敏诊断的拒绝原因与字段路径，先核对报文再增加适配，不全局放行 |

所有兼容均不得跳过认证、设备/通道归属、Call-ID/tag/CSeq、重复字段与冲突检查。已知字段乱序及无冲突 Info 的顺序规范化作为通用接收兼容；涉及字段含义变更、非标准位置或订阅必填参数缺失的适配，仅对明确配置的设备档案开启。身份和对话错误不能通过“兼容模式”修复。

协议版本仍为 1.0/1.1/2.0/3.0 对应的声明及有效版本，不通过降级协议规避厂商差异。接收规范化后的内容发往上级或本域接收者前，重新按目标版本编码与验证，不直接透传兼容报文。

## 8. 实施顺序与验收

| 批次 | 内容 | 完成判据 |
|---|---|---|
| 第一批：恢复可用性 | 空指针、合法接纳快照、独立事件入库重试、历史恢复入口 | 四版合法报警均能入库；确认后崩溃/重启和数据库短时不可用后自动恢复；重复恢复不增加事件 |
| 第二批：业务一致性 | 业务身份、双方式关联、独立副作用任务 | 重传幂等；并发双报及重启不产生重复业务事件；连续同秒报警不被错误合并 |
| 第三批：接收管理 | 持久策略、布防协调、订阅复用及状态页面 | 设备/服务重启后恢复；拒绝和部分成功可见；关闭不会误撤防或取消他人订阅 |
| 第四批：兼容完善 | 各版本接收规范化、按设备档案适配、诊断 | 指定变体接纳；身份伪造、冲突字段、未知对话仍拒绝；对外报文继续通过目标版本严格校验 |

第一批事件身份与任务格式为后续批次预留版本字段；不先用有误吞风险的时间窗口去重。历史恢复在新入库链路稳定后执行，恢复清单按最终选定的去重策略复核。

自动化复用现有报警、订阅、重试和事件唯一键测试，仅补关键缺陷回归：确认后进程中断、任务重放、并发双报、同秒连续报警、设备删除后重建、兼容字段冲突及旧任务迁移。代码回放通过不等于四版本厂商真机验收通过。

现场先用当前海康 2022 设备验证新报警入库、重启恢复和双方式上报；2011/2014/2016 使用相应真机或已取得的真实报文验证，缺少真机明确列为未验证。

发布优先仅更新 A 端。现有证据显示 B 能正常转发报警，不为此次修复无依据修改 B。新增字段采取可选 JSON 扩展和带版本键，保留旧数据；涉及新任务处理的版本回滚需确保旧服务不会消费其无法理解的任务，未完成任务保留待新版恢复。
