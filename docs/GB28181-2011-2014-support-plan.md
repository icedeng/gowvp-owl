# GB/T 28181-2011/2014 支持开发方案

配套执行文档：[AI 开发执行计划](GB28181-2011-2014-ai-development-plan.md)。

## 1. 目标

在现有 GoWVP Owl 项目中，补齐以下两个协议档案：

| 协议档案 | SIP `X-GB-Ver` | 说明 |
|---|---:|---|
| GB/T 28181-2011 | `1.0` | 基础标准 |
| GB/T 28181-2011 修改补充文件（2014） | `1.1` | 2011 版修改补充文件，不是独立的 GB/T 28181-2014 国家标准 |

现有 2016/2022 能力继续保持兼容。实现目标不是复制一套旧代码，而是在同一套 SIP、事务、设备、媒体和业务模型上增加协议档案和能力分派。

## 2. 依据和范围

依据文件：

- [GBT-28181-2011.pdf](GBT-28181-2011.pdf)
- [GBT-28181-2014.pdf](GBT-28181-2014.pdf)
- [GBT-28181-2016.pdf](GBT-28181-2016.pdf)
- [GBT-28181-2022.pdf](GBT-28181-2022.pdf)

2022 版附录 I 给出的版本对应关系为：`1.0=2011`、`1.1=2011 修改补充文件`、`2.0=2016`、`3.0=2022`。版本号应作为协议协商标识使用，不应直接当作普通年份排序。

本方案覆盖：

1. 设备注册、注销、Digest 鉴权和版本协商；
2. 心跳、设备信息、目录、报警、状态和订阅通知；
3. 实时点播、录像检索、回放和下载；
4. PTZ、语音广播、设备配置及 2014 补充命令；
5. SIP/SDP/XML 报文兼容和多厂商互通测试。

本方案不承诺 S/MIME 全量实现、所有厂商私有扩展和正式检测认证。数字证书双向 REGISTER 已作为后续专项在同一项目实现，但真实 CA/CRL、设备和上级平台互通仍需单独验收。

### 2.1 关键假设

- 原第一阶段以“平台作为 SIP 服务端接入下级 IPC/NVR/网关”为目标；后续工作包已经加入本平台向上级注册、目录共享、媒体转发和标准事件订阅。
- 现有媒体服务器继续承担 RTP 端口分配、PS/音频流接收、语音 RTP 发送和流生命周期管理。
- 开发期间至少能获得两种 1.0 设备和两种 1.1 设备或等价设备模拟器。
- 级联工作包已进入实现：支持四版本基于 UDP/TCP/TLS 的上级注册、目录共享、直播、回放/下载以及 Catalog/Alarm/MobilePosition/PTZPosition 订阅；`SIPUpstream.transport` 为空默认 UDP，可显式选择 TCP 或 TLS 并复用持久连接完成 Digest、心跳和后续级联信令。出向 TLS 默认校验系统 CA，可配置独立 CA、服务端名称和客户端证书/私钥；入向 SIP-TLS 可配置客户端 CA，并可强制拒绝无证书或不受信任证书，实现传输层双向 TLS。2022 注册支持 301/302 的 UDP/TCP/TLS 与 `sips:` 重定向，并拒绝从 SIPS 降级到明文传输。Catalog 查询/订阅支持平台根和单个共享通道，按 2011 `Response`、2014+ `Notify` 根发送 ADD/DEL/ON/OFF/UPDATE 增量；上级事件订阅会自动建立、续订、复用和取消真实下级订阅。上级订阅对话与下级引用表均按订阅键串行网络操作，无关设备/事件可并行；在途创建使用占位状态，关闭会等待它收敛后再退订，不会遗留刚创建的下级订阅。事件 NOTIFY 使用独立串行锁与上级 worker 生命周期 context，热更新或关闭上级时不会被在途 NOTIFY 响应等待阻塞；真实平台互通和生产验收仍需单独排期。

### 2.2 当前实现状态（2026-08-26）

- `1.0/1.1/2.0/3.0` 共用同一套版本协商、能力门禁、SIP/XML/SDP 和设备模型；不需要拆分独立项目。
- 2011/2014 代码能力已完成自动化和本地模拟器覆盖，但真实设备矩阵、目标环境灰度和正式检测认证仍未完成。
- 四版本媒体 SDP 已同时支持 IPv4/IPv6：直播、回放、RTP 下载、2014 直接 TCP 下载、广播、对讲以及级联视频/语音会按地址生成 `IP4` 或 `IP6`，入向直接 TCP 地址继续执行同设备/CIDR、组播及链路本地安全检查；IPv4 报文字节保持兼容。
- 四版本 SIP 信令已支持 IPv4/IPv6 宣告：显式 `Sip.Host` 优先，无配置时保持 IPv4 优先并在 IPv6-only 主机回退全局 IPv6，探测失败时使用 `Media.SDPIP`；SIP URI、Via、From、To、Contact 和 Route 内部统一保存裸 IPv6，写出时按 RFC 3261 自动加方括号，避免双重方括号和 `localhost` Via。IPv4 URI/Via 输出保持兼容，并已覆盖真实 `[::1]` UDP 监听与出站请求测试。
- 设备使用 UDP/TCP/TLS 注册或保持在线后，平台主动 MESSAGE/INVITE/BYE/OPTIONS 等请求会按当前连接生成一致的 Via transport；TLS 在连接包装层保留独立信令传输元数据，不再因底层地址报告 `tcp` 而降级为 TCP/UDP。设备持久化 transport 同步区分 `udp/tcp/tls`，服务重启时 TCP/TLS 会统一标记离线，避免复用失效的流连接。
- SIP/TCP 服务端已覆盖大小写不敏感 `Content-Length`、紧凑头 `l` 和同连接连续报文分帧；对话内 ACK/BYE 按 RFC 3261 反转 `Record-Route` 建立路由集且不再污染原响应 CSeq。
- 2014 语音广播按附录 Q 实现“接收者主动 INVITE”，使用 ZLMediaKit 中已就绪的 G.711 A-law 音频流作为语音发送者；`1.1` 使用 `PT 96/PS/90000`，`2.0/3.0` 使用 `PT 8/PCMA/8000`。
- 2016/2022 语音对讲在设备音频流建立后复用同一 RTP 连接反向发送 G.711 A-law 音频；LALMAX 已通过 `stat/group` 提供媒体源状态和 RTP 下载进度，并通过 `stop_rtp_pub` 主动释放接收会话。对 LALMAX 官方公开源码提交 `0845640`（2026-05-28）的核验确认其仍未提供 RTP 发送接口，因此语音发送明确返回不支持，不猜测私有端点。其公开的 ZLM 兼容层已支持关闭流及开始/停止录像，Owl 会携带配置 token 调用这些接口并通过真实配置查询探测节点健康；上游仍未提供带录像状态的完整流列表，自动录像状态同步对 LALMAX 明确返回不支持，不再用空列表伪装成功。
- 上下级平台级联仍按独立验收工作包管理，但代码已在同一项目内实现，不另起项目。
- 指定路径及语音级联使用的 `cascade-*` 独立媒体流无需持久化通道记录也能接收注册/注销事件，断流时会正确收敛 SIP/RTP 会话。媒体节点只有在连接、Hook 配置和状态持久化全部成功后才发布在线；初次失败不会因新缓存时间戳误报在线，后续探测恢复会重做完整配置而非只做 Ping。数据库更新失败会返回错误而不再由后台 goroutine `panic`，节点检查器随应用清理幂等退出。
- 2014 广播需要的接收者主动 `INVITE` 已实现；已注册上级的通用入向 `INVITE` 进入级联 B2BUA，未知来源仍明确返回 `501`。
- 入向级联及广播对话按 `Call-ID + 远端 From tag + 本地 To tag` 绑定；ACK 必须使用原 INVITE CSeq，CANCEL 还必须匹配原 INVITE 的 CSeq、Request-URI、顶层 Via 协议/传输/Sent-by/branch，BYE/INFO 使用严格递增的远端 CSeq。合法 INFO 重传复用原响应且不重复下游控制，同 CSeq 改报文或跨方法回放返回 `500 CSeq out of order` 且无媒体副作用；已注册来源不能通过复用 Call-ID 操作另一对话。
- 本平台主动发起的设备直播/回放/下载/对讲及级联语音源会话同样按 2xx 建立的双向 tag 校验入向 BYE；仅设备号、来源和 Call-ID 相同不能跨对话终止媒体。
- Alarm 订阅已支持级别、方式、类型和时间过滤；`AlarmType` 按 2016/2022 门禁，2011 附录 J 示例的 `StartTime/EndTime` 作为兼容别名接收。
- 设备及上级事件订阅会话按订阅方、`Call-ID`、双向 tag、事件类型和目标共同隔离；创建请求必须不带 `To tag`，续订和 `Expires=0` 取消必须复用服务端建立的 `To tag` 并递增 SUBSCRIBE CSeq。其他设备或上级复用部分对话字段、回放 CSeq 或取消不存在的对话时返回 `481`，不能覆盖、续订、改变过滤/下游引用或取消原订阅。
- 出向 SUBSCRIBE 续订/取消以及向设备、上级发送的 NOTIFY 已完整复用订阅对话的 Call-ID、双向 tag、递增 CSeq、Contact 远端目标和 Record-Route；UAC 按响应逆序、UAS 按请求原序建立路由集，并同时支持宽松/严格路由。设备 NOTIFY 使用当前注册连接，上级 NOTIFY 根据实际目标保持 UDP/TCP/TLS，不再硬编码降级为 UDP；同一订阅的并发 NOTIFY 串行分配唯一 CSeq。
- 入向标准事件订阅只接受四类命令：2011+ `Alarm`/`Catalog`、2016+ `MobilePosition`、2022 `PTZPosition`。查询、状态、广播命令及任意 `Query`/`Status` 后缀扩展不再伪装成事件订阅。
- SUBSCRIBE 创建、续订和 `Expires=0` 取消统一要求 `Query` 根、正 `SN`、20 位 `DeviceID` 以及与正文命令/目标匹配的必填 `Event`；空目标不再扩大为内部通配订阅。取消请求完成相同包络校验，但允许旧版本清理已经存在的高版本事件对话，不受创建能力门槛阻断。
- 标准 Alarm/Catalog/MobilePosition/PTZPosition 的入向 `NOTIFY` 必须绑定本平台真实发出的 SUBSCRIBE 对话，同时匹配已鉴权设备、订阅目标、`Event`、`Subscription-State=active/pending/terminated`、Call-ID、双向 tag、递增 NOTIFY CSeq 和有效期；不匹配时返回 `481`，不得写状态、触发回调或向上级转发。兼容 RFC 6665 允许首个 NOTIFY 早于 SUBSCRIBE 最终响应的时序，首个合法请求只绑定一次远端 tag；升级、抓拍完成和 VideoUploadNotify 等独立业务通知不套用订阅对话门禁。
- NVR 代表已知子通道返回 `DeviceInfo` 时更新子通道元数据，不再因 SIP From 为父设备而误拒绝，也不会覆盖父设备信息。
- 支持通过设备编辑接口的 `gb_disabled_capabilities` 单独关闭固件未实现的扩展能力；运行时门禁、设备能力快照和诊断接口均使用过滤后的有效能力集。
- 注册后的自动 `ConfigDownload` 同样遵循 `config_query` 设备能力关闭项；设备查询与控制 SN 统一使用正整数单调序列，并在有符号 32 位上限安全回绕，避免自动查询与人工查询串包。
- REGISTER `Date`、RecordInfo 查询/解析与录像分日、报警和级联时间统一按标准规定的北京时间处理，不再依赖容器本地时区。RecordInfo 未收到任何业务响应时明确返回超时，只有收到完整 `SumNum=0` 才表示无录像；重叠录像段和午夜边界按有效时间段合并、分日。
- 2022 设备升级已补齐 `DeviceUpgradeResult` 最终结果处理和会话状态查询；图像抓拍已补齐受约束 HTTP 上传、`UploadSnapShotFinished` 最终通知和会话状态查询，不能再仅凭业务受理应答报告完成。两类最终通知均绑定已鉴权设备、`SessionID` 和原目标通道，同一 NVR 的兄弟通道不能复用会话编号覆盖终态。
- 2022 升级以 `DeviceUpgradeResult` 的 completed/failed 为权威最终状态；最终通知先于控制业务应答到达时，迟到的 accepted/rejected 不会覆盖最终结果。
- 2022 升级/抓拍会话状态按 7 天 TTL 和 1024 条上限回收，小时清理器与查询惰性清理共同保证无新任务时也能删除过期状态；抓拍上传计数使用锁内原子读改写，多个图片并发上传不会丢计数，迟到上传不会把完成/失败终态回退为 uploading。
- 2022 抓拍在命令发送前预登记 pending 会话，兼容设备先上传图片或发送完成通知、后返回 DeviceConfig 业务应答的时序；抓拍目标必须是在线设备自身或其已知子通道。公开上传入口限制总请求体 10 MiB、实际图片 5 MiB，避免未鉴权回调被无界读取占用内存。
- 2016/2022 看守位控制校验 `Enabled=0/1` 和 `PresetIndex=0..255`；2022 PTZ 精准控制拒绝非有限值并校验 `Pan=0..360`，云台控制附加参数按版本门禁并限制巡航轨迹名称最长 32 字节，报警复位按 `0` 或 `1..7` 的 `/` 组合校验方式，并按单一方式 `2/5/6` 校验报警类型。升级最终通知校验 `SN`、`Result=OK/ERROR`、必填固件以及失败原因 `01/02/03/99`，抓拍完成通知校验正序号、命令类型和最多 10 个文件标识。
- 2022 已补齐 TargetTrack、VideoUploadNotify、八类扩展 DeviceConfig 写入及 H.265/AAC SDP 能力；VideoUploadNotify 校验固定命令类型、正序号、必填设备编码和时间、有限经纬度，并只接受已鉴权设备自身或其已知子通道。3.0 未指定音频编码时使用标准完整占位 `f=v/////a///`，设备可选择 G.711、SVAC 或 AAC。
- 注册重定向目标只读取服务端 `Sip.RegisterRedirect` 配置，并仅对声明 3.0 的 REGISTER 生效，不信任设备请求头提供的跳转地址。
- 标准四版本的低安全级别 REGISTER 口令摘要认证已具备服务端 nonce 生命周期、设备/源 IP 绑定、重放限制和算法一致性校验；服务端保持 MD5 设备兼容，级联客户端支持 MD5/SHA-1/SHA-256 挑战。2016 `Capability/Asymmetric` 数字证书 REGISTER 已形成服务端和级联客户端自动化闭环：按设备国标编码固定映射证书或校验 CA 链，支持 CRL、有效期、两段 Base64 nonce、MD5/SHA-1/SHA-256、源地址绑定、重放防护及 Required 防降级；该能力与 SIP-TLS 证书相互独立并默认关闭。除 REGISTER 外的 `Date + Note` 信令摘要已完成设备侧和级联侧请求/响应闭环：按 `From + To + Call-ID + Date + seed + 消息体` 计算，校验北京时间时间窗，支持 MD5/SHA-1/SHA-256/SM3、Base64 输出及可选十六进制兼容；SM3 采用成熟国密库并通过 GB/T 32905 已知向量测试。设备独立密码优先，上级使用 `SignalDigestSeed → Password → 全局 Seed`。四版本共同规定的 `Monitor-User-Identity` 已形成自动化闭环：按每个上级配置本地/直接上级 211 类型安全路由网关、真实用户 ID、机构/类别/职级及可信中间网关，支持本域生成、跨域逐级前置、下行转发、事务响应统一回传、直接网关与源平台注册绑定、跳数/环路/重复网关校验和用户属性白名单访问控制；身份与 `Date + Note` 可在同一事务组合验证和签名。Required 模式至少配置一项授权白名单，默认关闭。该能力仍需真实安全路由网关及用户目录互通，2022 高安全级别还需按 GB 35114 单独验收。
- SIP URI、Via、To/From/Contact/Route 地址解析已对短字符串、纯空白、空用户/主机、缺失引号或 `>` 等畸形输入返回明确错误；解析后的 IPv6 主机统一为裸地址，序列化时自动使用方括号，模糊测试用于持续验证解析入口不 panic。直播、回放、下载、广播、对讲和级联媒体的 SSRC 生成不再直接切片域编码，而是校验 10 位数字域并显式传播配置错误。
- 从设备 2xx 响应创建 ACK/INFO/BYE 前统一校验 To、From、Via、Call-ID、CSeq 和目标 URI；只缺 Contact 时按老设备兼容策略回退 To，其他必需字段缺失时向直播、回放、下载、广播、对讲和级联调用链返回错误，不再因空指针导致会话 goroutine panic。对话路由同时实现 RFC 3261 宽松/严格路由：响应 Record-Route 逆序建立路由集，首 Route 无 `lr` 时改写 Request-URI 并把远端 Contact 追加到 Route 尾部；新 Via 去除响应侧 `received/rport` 值并生成新 branch。设备 TCP 重连后复用当前连接但不覆盖对话路由目标。
- SIP 响应从请求复制并克隆 To 头后再生成服务端 tag，不再反向修改原请求；级联 INVITE 缓存响应只对 CSeq、Request-URI 和顶层 Via 均相同的原事务重传复用，相同 Call-ID/tag 的另一事务返回 `491`。
- SIP 事务发送缓存响应时先克隆再附加 `Date + Note` 或 `Monitor-User-Identity` 安全头，重传并发不会改写共享缓存响应或发生跨事务签名污染。
- 设备发起的 MediaStatus/121 和 BYE 结束历史媒体时，同时校验已鉴权设备编号与会话所属设备；仅 Call-ID 相同不能跨设备终止 RTP 回放/下载或 2014 Direct TCP 下载。
- 入向 SIP 请求在进入验签和业务 handler 前要求 `SIP/2.0`、恰好一个有效的 From、To、Call-ID、CSeq、`SIP/2.0` 顶层 Via，并要求 Request-Line 方法与 CSeq 方法一致；不支持的 SIP 版本返回 `505 Version Not Supported`，其他缺失、重复、无效或方法错配使用独立临时事务返回 `400 Bad Request`（畸形 ACK 静默丢弃），不会借复用 Call-ID/CSeq 改写合法事务的连接或响应安全器，也不再继续执行半初始化上下文。
- 入向 SIP 响应同样要求 `SIP/2.0`、100～699 状态码、From/To/Call-ID/CSeq 各有且仅有一个有效值和 `SIP/2.0` 顶层 Via；出向事务记录目标端点以及 Via 协议/传输/Sent-by/branch，只有结构、事务和来源全部匹配的响应才能唤醒业务等待。Via 参数名按大小写不敏感处理，缺失 branch 的出向请求会在发送前补齐，重复 branch、重复核心头、错误 branch 或错误来源响应直接丢弃；等待最终结果时跳过全部 1xx 临时响应，不再把 `180 Ringing` 等误认为最终响应。
- 对话本地 SIP CSeq 由响应关联状态并发安全地逐次递增，连续 INFO/BYE 不再重复使用 `INVITE CSeq + 1`；2xx ACK 复用 INVITE CSeq 但使用新 branch，3xx～6xx INVITE 最终响应自动发送复用原 INVITE Request-URI/Via branch/CSeq 的事务内 ACK。等待 INVITE 的调用方取消或超时时自动发送独立 CANCEL 事务，CANCEL 复用原 INVITE Request-URI、Route、Via、Call-ID、From/To 和数字 CSeq；禁止从响应错误构造 CANCEL 或非 2xx ACK。
- 每条 SIP/TCP 连接的解析器停止时会关闭其输出通道，`handlerListen` 随通道结束退出，避免设备频繁断线重连后永久遗留一个 handler goroutine。
- SIP Server 统一登记已经建立的设备及上级 TCP/TLS 连接；`Close` 并发幂等地取消服务、关闭监听器、活动连接和事务，阻塞读取会被解除并退出，不再只关闭监听端口而遗留既有连接。
- SIP/TCP 采用有界逐行读取：单头行 8 KiB、总头 64 KiB、SIP 正文 1 MiB；UDP 解析使用相同正文上限，并要求 `Content-Length` 与数据报正文精确一致。超限/重复长度、截断正文和声明零长度后的尾随正文在分配或业务分派前拒绝；2014 附录 O 的文件数据使用独立裸 TCP 链路，不受 SIP XML 正文上限影响。
- 设备 Keepalive 在 XML 解析和内存态落定后立即返回 `200 OK`，然后再执行设备/历史持久化、订阅 NOTIFY 转发和首次 Catalog 补载；省略 `Status` 的兼容心跳在结构化状态与持久状态中均一致视为在线。Alarm、MobilePosition、DeviceInfo、DeviceConfig、ConfigDownload 及通用查询响应同样先更新内存快照并解除查询等待、确认入向 SIP 报文，再执行附录 A.4 数据库写入、外部回调和订阅转发；同一通用查询报文只解析和持久化一次。慢数据库、订阅方、业务回调或目录超时不再拖延设备确认、触发重传或造成心跳误离线。
- 通用查询严格区分 SIP 方法和 XML 根：`MESSAGE` 查询应答只接受 `Response`，订阅 `NOTIFY` 事件只接受 `Notify`；两者均校验正 `SN`、命令类型、版本能力和目标所有权。合法事件通知可以更新状态和转发订阅，但不能解除 `MESSAGE` 查询等待；2022 `VideoUploadNotify` 等独立业务通知仍按其专用包络处理，不套用查询应答矩阵。未知跨设备编码不能产生任何副作用。2014 `PersetQuery` 历史拼写继续规范化为 `PresetQuery`。
- 通用查询 NOTIFY 路由只保留 2022 `PTZPosition` 事件；DeviceStatus、Preset/HomePosition/CruiseTrack/SDCardStatus/ConfigDownload 等查询或状态命令只作为 `MESSAGE + Response` 处理，不能由 `NOTIFY` 写状态或转发为订阅事件。查询应答也不再调用事件发布链路。
- 通用查询在产生状态、解除等待或转发订阅前校验业务载荷：预置位、巡航轨迹和存储卡的必填字段及列表计数必须一致；看守位开关和预置位范围、巡航编号/名称/速度、PTZ 有限浮点数、存储卡状态/进度/容量均按标准约束。2014/2016 的预置位应答继续允许不携带 2022 新增的 `SumNum`，保留老版本兼容。
- DeviceInfo 四版本应答复用通用包络和目标所有权校验，并额外约束固定命令；非法应答不能覆盖父设备/子通道信息或唤醒查询等待。
- DeviceInfo 四版本均按标准要求固定 `Response` 根和必填 `OK/ERROR` 结果，空 Result 不再被当作成功后覆盖设备/通道元数据；DeviceControl、Broadcast、Upgrade、Snapshot 和 ConfigDownload 的公开等待路径也不再保留空结果成功兜底，防止内部或未来入口绕过协议校验。
- DeviceStatus 四版本应答按标准校验必填的 `Result=OK/ERROR`、`Online=ONLINE/OFFLINE` 和 `Status=OK/ERROR`；失败结果及子通道状态不再改写父设备在线运行态。
- DeviceControl 四版本及 Broadcast 2014+ 应答校验 `Response` 根、固定命令、正 SN、必填结果枚举和目标所有权；响应目标还须与对应在途控制/广播请求一致，非法应答不能解除等待。
- Keepalive 四版本在补载设备和写在线态前校验 `Notify` 根、固定命令、正 SN、源设备一致性及故障设备编码；标准 `OK/ERROR` 外继续兼容已记录的空值、`ON/OFF` 厂商状态。
- Alarm 四版本在附录 A.4、业务回调和订阅转发前校验 `Notify` 根、固定命令、正 SN、目标所有权、报警级别/方式/时间及有限经纬度；非法报警不产生任何业务副作用。
- MediaStatus 四版本校验 `Notify` 根、固定命令、正 SN、必填设备与通知类型，并在可找到会话现场时强绑定父设备/通道和 Call-ID；未知通知类型及已清理会话的重复 `121` 保持幂等确认，非法目标不能结束媒体任务。
- RecordInfo 四版本在进入多响应聚合器前校验 `Response` 根、固定命令、正 SN、20 位目标、必填名称、非负总数及 `RecordList Num`；响应和条目目标必须属于已鉴权父设备，并与在途通道查询一致。兼容部分 NVR 顶层回写父设备编码、条目仍使用查询通道编码，非法分包不能污染或提前完成查询。
- MobilePosition 仅对 2016+ 设备开放；通知在写状态和订阅转发前校验 `Notify` 根、固定命令、正 SN、目标所有权、必填时间、有限经纬度及 `[0,360)` 方向角。2022 的 `SumNum + DeviceList Num + Item` 批量位置已结构化保存，同时保留原单点 `mobile_position` 字段兼容既有 API；2011/2014、非法计数和未知子通道不会产生状态副作用。
- ConfigDownload 在修改运行态前执行同一套响应校验；成功响应携带 BasicParam 时，心跳间隔和超时次数必须同时位于 `1..65535`，非法值不再被截断、修正或静默忽略，且不能写状态或解除等待。失败响应和子通道 BasicParam 不会改写父设备心跳运行态。
- DeviceConfig 与 ConfigDownload 严格要求标准 `OK/ERROR` 结果枚举，空值不再被当作成功；DeviceConfig 在写查询状态和解除等待前绑定原始目标通道，同一 NVR 的兄弟通道不能复用 SN 抢占配置/抓拍应答。
- DeviceConfig 应答按 2014+ 门禁并校验根节点、固定命令、正 SN 和目标所有权；非法应答不能写入状态、附录 A.4 或唤醒等待。
- Catalog 查询响应和变化通知同样校验根节点、固定命令、正 SN、20 位顶层目标及非负 SumNum；2014 目录树的合法行政/系统根编码继续兼容，非法目录不会进入多响应聚合或解除查询等待。
- Catalog 进一步区分缺失 `SumNum` 与合法零值，校验 `DeviceList Num`、本包条目数、通知总数、条目编码和已鉴权来源；父设备目录查询不会接受已知子通道用相同 SN 注入的分包。通用查询等待同样记录原始目标，兄弟通道响应不能写状态或抢先解除等待。
- 上级级联查询在返回 SIP `200` 和启动下级任务前校验 `Query` 根、正 SN、20 位目标、已支持命令及命令专属必填字段；RecordInfo 必须携带递增的有效时间范围，CruiseTrackQuery 必须显式携带 `0/1` 轨迹编号，MobilePosition 不接受负上报间隔。非法请求不再被异步转发或伪装为空业务响应。
- 2022 `DeviceUpgradeResult`、`UploadSnapShotFinished` 和 `VideoUploadNotify` 按标准固定 `Notify` 根并要求 20 位设备编码；抓拍完成通知要求存在 `SnapShotList`，其中任何非法文件标识会拒绝整条通知，不再静默丢弃后生成错误终态。
- 下级主动发送的 `Subscription-State: terminated` NOTIFY 还必须匹配 Event、订阅目标及递增 CSeq；仅复用 Call-ID 的其他设备或对话不能删除并触发重建真实下级订阅。终止与并发刷新/重建按对话实例隔离，旧终止请求不能删除或重复创建新对话。
- 同一设备的 REGISTER 查询、鉴权、首次自动建档和状态提交按设备串行，不同设备互不阻塞；多实例并发首次建档发生唯一键竞争时回读已创建记录，UDP 重传或并发 REGISTER 不再因重复建档误回 `500`。完全相同且同源的成功事务重传在有界短期缓存中复用原 `200/Date`，不重复写注册历史或触发 DeviceInfo/Catalog；认证头、Expires、源地址等发生变化时仍按新请求处理。
- SIP/TCP/TLS 长连接空闲等待首字节不设置超时，兼容低频心跳；一旦收到首字节，完整 SIP 头和正文必须在 30 秒内读完，超时关闭连接，避免慢速逐字节请求长期占用 goroutine。
- XML 的 UTF-8→GBK/GB18030 厂商兼容回退改为临时对象原子解码：首轮失败时不会把已解析的部分目录/录像切片留在目标中，第二轮成功不会产生重复项，两轮均失败也不会污染调用方已有状态。
- 省略显式 `Sip.Domain` 时，REGISTER 和 MESSAGE/NOTIFY Digest 挑战、验签以及回放响应补写的 Contact 均统一使用平台 ID 前 10 位派生域。两类 Digest 验签都会在计算前保存客户端原始 `response`，拒绝错误口令；兼容 MESSAGE/NOTIFY Digest 还绑定 realm、username、请求 URI、方法、设备和源 IP，并通过有界、限时 nonce 与递增 `nc` 防止跨请求重放。
- SIP 配置启动加载和 API 更新统一校验 20 位平台 ID、10 位有效域、端口、TLS 必填项、设备历史范围、信令摘要及上级 `Monitor-User-Identity` 身份/授权策略。API 先原子写盘再提交运行时快照，写入失败不会污染内存；Host、平台 ID/域、监听端口、TLS 和 SIP 报文日志等需要重建监听器、身份或全局日志器的字段明确要求修改文件后重启，其余鉴权、摘要、历史、2014 直连下载和上级级联配置使用并发安全快照热更新。
- SIP UDP/TCP/TLS 在应用构建阶段同步绑定并显式返回地址、证书或端口占用错误，持久化设备/通道恢复错误也沿构建链路返回，不再由后台 goroutine 或缓存加载 `panic`；部分启动成功后的监听器会统一回收。设备离线检查也随 GB28181 服务生命周期停止，避免停服后遗留永久定时 goroutine。
- Catalog 完整快照会先校验全部目录/通道目标可安全构造 SIP URI，发现控制字符或空目标时拒绝整份快照而不是部分覆盖，同时保留安全的厂商非标准编码兼容；持久化恢复与统一出站请求入口还会校验目标连接和目的地址，避免畸形厂商目录在后续点播或查询时触发空指针。
- 在线设备的注册、心跳、连接、地址、口令和离线时间统一由受锁运行态维护；同一设备的数据库更新与运行态同步作为一个串行操作提交，OPTIONS 只有在设备返回 `200` 且活动时间成功提交后才算探测成功。离线扫描在落库前复核注册/心跳代次，旧扫描不能覆盖刚完成的 REGISTER、Keepalive 或 OPTIONS 探测。服务重启恢复设备时同步恢复注册 `Expires`。媒体、查询、控制、摘要和级联调用读取一致快照，出站请求一次取得同代 To/连接/目的地址，避免重注册和并发心跳期间的数据竞争或跨连接组包。
- SIP 报文日志器只在所有监听器启动成功后切换；并发报文写入与关闭使用同一互斥锁，启动回滚和停服不会关闭仍在写入的输出对象。
- RTP 下载终态、2014 裸 TCP 下载终态和设备结构化查询快照均增加 TTL 与容量上限；小时清理器随 GB28181 生命周期退出，无新任务时也能回收过期状态和文件，活动下载及其 `.part` 文件不会被误删。GB28181 服务关闭时会永久关闭 2014 裸 TCP 下载管理器，取消并等待活动下载及其连接取消 watcher 全部退出，关闭后拒绝新下载。结构化查询读取及 `DeviceQuery` 返回值均包含嵌套切片、指针和 A.4 字段映射的深快照，诊断/API/SDK 调用方不能改写内部运行态，也不会与后续报文合并产生数据竞争。
- 服务关闭会幂等释放普通直播、回放/下载、广播、对讲和级联媒体资源；直播/历史 RTP 端口打开失败或主动停止半初始化会话时不会遗留占位流或 RTP 接收端口，即使设备 2xx 畸形无法构造 BYE 也继续完成媒体端清理。MediaStatus `NotifyType=121` 和普通出站媒体的入向 BYE 均先原子删除会话并设置终态、再确认对端，媒体服务器关端口、下载进度刷新和播放状态写库放在确认之后，慢外部清理不再导致重传。级联 INVITE 清理器只回收长期未建立的半开会话，已建立的长时直播/回放不再因 10 分钟没有 SIP 控制消息而被误切断。
- 服务关闭会立即取消 PTZ、设备控制/查询/配置、升级、抓拍、广播、级联媒体/语音和 Catalog/RecordInfo 等业务等待，清空在途请求、响应别名及订阅索引，并禁止继续创建出站 SIP 请求，不再依赖各业务 6～10 秒超时自行退出。全局 SIP 生命周期中间件将已经接纳的 REGISTER/MESSAGE/NOTIFY/SUBSCRIBE/INVITE 等请求纳入关闭等待，并从停服开始起拒绝新业务；关闭采用“停止接纳并取消业务 → 注销级联并关闭 SIP 以解除事务/连接等待 → 等待 handler → 清理 GB 会话索引”的两阶段顺序，避免清理后又写回运行态或在等待 handler 时互锁。上级级联广播、控制、查询、初始/增量目录 NOTIFY、terminated 订阅续订及设备 Catalog NOTIFY 后刷新统一纳入 GB28181 生命周期；关闭与任务接纳串行化，避免 `WaitGroup.Add`/`Wait` 竞态，关闭会取消并等待在途任务且拒绝新任务。级联 NOTIFY 同时继承调用方和上级 worker 的取消信号，不会绕过 30 秒调用超时或停服取消。
- Web/Adapter 传入的调用方 `context` 已贯通实时点播、历史回放/下载、控制、查询、配置、订阅、升级、抓拍和语音等 SIP 最终应答及业务等待；级联实时点播也将入向 INVITE 会话取消传播到下级点播，上级 CANCEL 后不再继续占用下级 SIP 事务和通道媒体锁。已取消请求不会继续发送命令，等待中取消会关闭对应事务并立即释放调用链，同时保留旧无 context 方法的向后兼容入口。
- 同一通道的直播、回放/下载、2014 直连下载、广播、对讲及停止操作保持串行，并支持 context 取消；锁由设备按通道 ID 引用计数管理，Catalog 替换通道对象时仍保持同一把锁，最后释放后自动删除。NVR 不同通道可并行，避免一个通道等待 SIP/媒体应答时阻塞整台设备。
- SIP 连接封装对空远端地址、非数据报底层连接及缺失出站连接/目的地址返回明确错误，不再通过类型断言或关闭错误包装触发 panic。

### 2.3 数字证书 REGISTER 配置边界

下级设备接入使用 `Sip.RegisterCertificateAuth`。`DeviceCertificates` 必须显式绑定 20 位设备国标编码，不能依赖证书 CN 猜测身份；`DeviceCA` 为空时固定信任映射证书，配置 `CRL` 时必须同时配置 `DeviceCA`。该运行态包含平台私钥、设备信任锚和 nonce 表，修改后必须重启：

```toml
[Sip.RegisterCertificateAuth]
Enabled = true
Required = false
PlatformCert = './configs/certs/platform.crt'
PlatformKey = './configs/certs/platform.key'
DeviceCA = './configs/certs/device-ca.crt'
CRL = './configs/certs/device.crl'

[Sip.RegisterCertificateAuth.DeviceCertificates]
'34020000001320000001' = './configs/certs/device-34020000001320000001.crt'
```

向上级平台注册在对应 `[[Sip.Upstreams]]` 下配置独立证书。`Required=true` 会隐式启用 Capability，并拒绝上级回落到 Digest 或未完成 Asymmetric 挑战就直接返回 200；该证书与 SIP-TLS 的 `TLSCert/TLSKey` 用途不同：

```toml
[Sip.Upstreams.RegisterCertificateAuth]
Enabled = true
Required = true
LocalCert = './configs/certs/cascade-local.crt'
LocalKey = './configs/certs/cascade-local.key'
ServerCert = './configs/certs/upstream.crt'
ServerCA = './configs/certs/upstream-ca.crt'
CRL = './configs/certs/upstream.crl'
```

### 2.4 Monitor-User-Identity 配置边界

2011、2016、2022 的 8.3 条款使用相同规则；2014 修改补充文件未修改该条款，继续沿用 2011。标准规定头值依次由一个或多个信令安全路由网关 ID、用户 ID、用户隶属机构、用户类别和用户职级组成，各段使用 `-` 分隔。因此属性值不得包含 `-` 或控制字符，网关 ID 必须是类型码 `211` 的 20 位编码，用户 ID 必须是类型码 `300-499` 的 20 位编码。

该策略按上级平台独立配置并支持热更新。`Required=true` 会隐式启用身份验证，并要求至少配置一项用户或属性白名单；直接上级网关同时与已注册上级平台的 SIP ID、源 IP 及 TLS 连接（如适用）绑定，不能仅凭头值获得信任：

```toml
[Sip.Upstreams.MonitorUserIdentity]
Enabled = true
Required = true
LocalGatewayID = '34020000002110000001'
RemoteGatewayID = '34030000002110000001'
LocalUserID = '34020000003000000001'
LocalOrganization = '340200'
LocalCategory = 'operator'
LocalRank = 'level1'
TrustedGatewayIDs = ['34040000002110000001']
AllowedUserIDs = ['34030000003000000001']
AllowedOrganizations = ['340300']
AllowedCategories = ['dispatcher']
AllowedRanks = ['level2']
MaxHops = 8
```

本域生成时使用配置的真实用户档案；转发外域身份时只在已验证的原值前添加本地网关 ID。系统拒绝重复头、非法分段、非 211 网关、非用户编码、不可信中间网关、重复网关、路由环、超跳和属性越权。应用层首先把直接网关绑定到已注册上级的 SIP ID、源 IP 及已验证 TLS 连接；使用 UDP/TCP 明文时仍应由部署网络提供标准要求的 IPsec 或等价可信边界，不能把源 IP 当作密码学身份证明。真实安全路由网关、用户目录及跨机构授权规则仍属于生产互通验收证据。

## 3. 当前实现基线和主要缺口

### 3.1 已有基础

- `pkg/gbs/sip` 已具备 SIP 消息、事务、UDP/TCP 监听、Digest 鉴权和 XML 编解码能力。
- `pkg/gbs` 已有注册、心跳、目录、设备信息、报警、录像、PTZ、语音、订阅和 INVITE 基础流程。
- 设备扩展数据已有 `GBVersion` 字段，数据库使用 JSON 扩展，不需要新增独立表。
- 2016/2022 已有部分版本门禁和 `X-GB-Ver` 下行发送逻辑。

### 3.2 必须先修复的问题

1. `pkg/gbs/sip/context.go` 只识别 `1.0/2.0/3.0`，缺少 `1.1`。
2. `pkg/gbs/catalog.go` 的 `wrapRequest` 没有 `1.1` 分支，未知版本默认发送 `3.0`，对老设备不安全。
3. 注册 `401`、`200` 和失败响应没有统一返回 `X-GB-Ver`。
4. 设备不携带版本头时，数据库版本可能被空值覆盖；内存默认版本和下行默认版本不一致。
5. 注册成功后无条件发送 `ConfigDownload`，纯 2011 设备可能不支持。
6. 目录模型缺失 2014 增加的 `ParentID`、`BusinessGroupID`、`IPAddress`、位置属性等字段。
7. 2014 的 `MediaStatus`、多响应、目录订阅、语音广播通知/应答、TCP 文件直传流程没有形成完整闭环。
8. 现有 SDP 主要面向 2016/2022，未按 2011 UDP 和 2014 TCP 下载规则选择构造方式。

## 4. 总体架构

### 4.1 协议版本模型

在 `pkg/gbs/version.go` 中增加规范版本类型，保留旧的 `2011/2016/2022` 展示兼容：

```go
type GBProtocolVersion string

const (
	GBVersion10 GBProtocolVersion = "1.0"
	GBVersion11 GBProtocolVersion = "1.1"
	GBVersion20 GBProtocolVersion = "2.0"
	GBVersion30 GBProtocolVersion = "3.0"
)
```

每个设备保存三个维度：

- `DeclaredVersion`：设备最近声明的 `X-GB-Ver`；
- `EffectiveVersion`：实际下行使用的协议版本；
- `VersionSource`：`header`、`manual`、`default` 或 `inferred`。

设备不携带版本头时不覆盖既有版本；首次遇到未知设备时使用可配置的保守默认值，默认建议 `1.0`。

### 4.2 能力矩阵

增加 `GBCapabilities`，业务判断能力而不是比较年份：

```go
type GBCapabilities struct {
	SupportsConfigQuery       bool
	SupportsCatalogExtension  bool
	SupportsDirectoryNotify   bool
	SupportsMultiResponse     bool
	SupportsMediaStatus       bool
	SupportsVoiceBroadcast    bool
	SupportsVoiceIntercom     bool
	SupportsRTPOverTCP        bool
	SupportsDirectTCPDownload bool
	SupportsH265               bool
	SupportsSnapshot           bool
	SupportsUpgrade            bool
}
```

建议初始能力映射：

| 能力 | 1.0 | 1.1 | 2.0 | 3.0 |
|---|---:|---:|---:|---:|
| RTP/RTCP over UDP | 是 | 是 | 是 | 是 |
| 设备配置查询 | 否 | 是 | 是 | 是 |
| 设备配置写入（Basic/视频/音频/SVAC） | 否 | 是 | 是 | 是 |
| 扩展目录字段 | 否 | 是 | 是 | 是 |
| 基础事件订阅/目录通知 | 是 | 是 | 是 | 是 |
| 多响应 | 否 | 是 | 是 | 是 |
| MediaStatus/121 | 是 | 是 | 是 | 是 |
| 语音广播 | 否 | 是 | 是 | 是 |
| 语音对讲 | 否 | 否 | 是 | 是 |
| RTP over TCP | 否 | 否（另有 TCP 下载规则） | 是 | 是 |
| 2014 直接 TCP 文件下载 | 否 | 是 | 厂商兼容扩展 | 厂商兼容扩展 |
| PTZ 精准位置变化订阅/通知 | 否 | 否 | 否 | 是 |
| 巡航轨迹列表/详情查询 | 否 | 否 | 否 | 是 |
| H.265/AAC、升级、抓拍 | 否 | 否 | 否 | 是 |

实际产品可通过设备手动覆盖和厂商兼容表修正能力。

### 4.3 版本协商

注册流程改为：

1. 解析设备 REGISTER 中的 `X-GB-Ver`；
2. 平台返回支持的最高版本，或返回协商后的有效版本；
3. 401、403、404、200 等注册响应都按协议要求携带版本头；
4. 记录设备版本来源和最终能力；
5. 后续所有 MESSAGE、NOTIFY、SUBSCRIBE、INVITE、INFO 使用同一份有效档案。

未声明版本的老设备：

- 允许通过管理端指定 `1.0` 或 `1.1`；
- 未指定时采用 `1.0 + UDP` 保守策略；
- 收到明确版本头后更新有效档案；
- 不因一次无版本心跳清空已有版本。

## 9. 发布策略

1. 第一个版本只开放 1.0/1.1 注册、目录、心跳和 UDP 实时点播。
2. 通过设备级开关逐步开放配置、订阅、语音和 TCP 下载。
3. 对 1.1 设备默认关闭 2.0/3.0 专属命令。
4. 日志中输出 `declared_version`、`effective_version`、`capability` 和失败命令。
5. 保留旧 API 和旧 JSON 字段，新增字段使用可选方式，不做破坏性数据库迁移。

## 10. 风险和应对

| 风险 | 应对 |
|---|---|
| 老设备不发送 `X-GB-Ver` | 手动版本覆盖、保守默认、厂商型号兼容表 |
| 设备声称 1.1 但只实现部分能力 | 能力按功能单独探测和关闭，不只信任版本号 |
| 2014 TCP 下载与 2016 RTP over TCP 混淆 | 两套独立 SDP/媒体流程，禁止复用同一个开关 |
| 目录扩展字段造成数据库兼容问题 | 先保存结构化字段和原始 XML，扩展字段采用 JSON 可选存储 |
| 现有 2016/2022 回归 | 四版本 golden 报文 + 原有设备回归矩阵 |
| 设备厂商私有 XML/编码差异 | XML 宽松解析、原始报文落盘、按厂商配置覆盖 |

## 11. 最终建议

继续在当前项目内实现，不独立复制项目。代码组织采用“公共协议核心 + 版本档案 + 能力矩阵 + 少量版本专用构造器”的方式。

第一开发阶段不应先实现所有 2014 新功能，优先修复 `X-GB-Ver 1.1`、注册响应和未知版本默认策略。完成版本协商后，再按 2011 基础能力、2014 补充能力、设备联调三个里程碑推进。
