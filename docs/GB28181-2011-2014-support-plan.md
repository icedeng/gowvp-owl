# GB/T 28181-2011/2014 支持开发方案

配套执行文档：[AI 开发执行计划](GB28181-2011-2014-ai-development-plan.md)。

## 1. 目标

在现有 GoWVP Owl 项目中，补齐以下两个协议档案：

| 协议档案 | SIP `X-GB-Ver` | 说明 |
|---|---:|---|
| GB/T 28181-2011 | `1.0` | 基础标准 |
| GB/T 28181-2011 修改补充文件（2014） | `1.1` | 2011 版修改补充文件，不是独立的 GB/T 28181-2014 国家标准 |

现有 2016/2022 能力继续保持兼容。实现目标不是复制一套旧代码，而是在同一套 SIP、事务、设备、媒体和业务模型上增加协议档案和能力分派。

## 2. 依据和范围

依据文件：

- [GBT-28181-2011.pdf](GBT-28181-2011.pdf)
- [GBT-28181-2014.pdf](GBT-28181-2014.pdf)
- [GBT-28181-2016.pdf](GBT-28181-2016.pdf)
- [GBT-28181-2022.pdf](GBT-28181-2022.pdf)

2022 版附录 I 给出的版本对应关系为：`1.0=2011`、`1.1=2011 修改补充文件`、`2.0=2016`、`3.0=2022`。版本号应作为协议协商标识使用，不应直接当作普通年份排序。

本方案覆盖：

1. 设备注册、注销、Digest 鉴权和版本协商；
2. 心跳、设备信息、目录、报警、状态和订阅通知；
3. 实时点播、录像检索、回放和下载；
4. PTZ、语音广播、设备配置及 2014 补充命令；
5. SIP/SDP/XML 报文兼容和多厂商互通测试。

本方案的“上下级平台级联”特指视频监控联网平台之间的设备目录、查询/控制、订阅和媒体业务。2011/2014/2016 规范性附录 G“联网系统与其他系统接口的消息格式”不是普通设备或平台级联功能：当前已在 `pkg/gbs/annexg` 补齐 `MPAlarm`、`ECSAlarm`、`TGSAlarm`、`ConfigDefence` 及三类 `*AlarmRecordList` 的严格 XML 协议层，并在 `pkg/gbs/annex_g_runtime.go`、`pkg/gbs/annexg/gormstore` 完成默认关闭的静态外部系统身份/角色/来源/Digest/TLS 门禁、生产 MESSAGE 路由、报警/查询/布控存储、管理平台主动连接器及按外部系统、命令、SN 关联的独立业务响应。2022 已删除附录 G，运行时明确拒绝。该部分已达到自动化代码链路完成，但真实综合接处警/卡口/城市信息系统互通、安全、性能和灰度仍未完成，不能声明生产支持。附录 G 继续使用同仓库独立协议/领域模块，无需另起项目；只有部署、数据权限或故障域必须隔离时才迁为独立服务。详细矩阵见 [附录 G 实现说明](GB28181-annex-g-implementation.md)。

本方案不承诺 S/MIME 全量实现、所有厂商私有扩展和正式检测认证。数字证书双向 REGISTER 已作为后续专项在同一项目实现，但真实 CA/CRL、设备和上级平台互通仍需单独验收。

### 2.1 关键假设

- 原第一阶段以“平台作为 SIP 服务端接入下级 IPC/NVR/网关”为目标；后续工作包已经加入本平台向上级注册、目录共享、媒体转发和标准事件订阅。
- 现有媒体服务器继续承担 RTP 端口分配、PS/音频流接收、语音 RTP 发送和流生命周期管理。
- 四版本标准的媒体面验收必须包含 RTP 控制协议（RTCP），不能只以 RTP 可播放作为完成依据。融合镜像和调试编排固定 ZLMediaKit 源码提交 `2fa539807370c4bcfca9801bde1dd2fdd95ba113`，并在构建时应用仓库补丁 `third_party/zlmediakit/patches/0001-gb28181-tcp-rtcp-rfc4571.patch`。补丁为收、发 RTP over TCP 会话增加默认关闭的 `tcp_rtcp` 开关：接收侧按 RFC 4571 解复用 RTP/RTCP、处理 SR 并周期发送 RR，发送侧处理 RR 并周期发送 SR；Owl 仅对 2016/2022 的 TCP 媒体会话开启，2011/2014 和全部 UDP 会话保持原行为，LALMAX 对开启请求明确返回不支持。`ZLM_IMAGE` 仍可显式覆盖默认构建阶段，但替代镜像必须实现同名 API 参数和同连接 RTP/RTCP 语义。补丁相关 ZLMediaKit 静态库和 Web API 已编译通过，仍必须以目标镜像、真实设备和真实上级平台抓包复核 SR/RR、丢包率及拥塞行为，不能据此声明生产媒体验收完成。
- 开发期间至少能获得两种 1.0 设备和两种 1.1 设备或等价设备模拟器。
- 级联工作包已进入实现：支持四版本基于 UDP/TCP/TLS 的上级注册、目录共享、直播、回放/下载以及 Catalog/Alarm/MobilePosition/PTZPosition 订阅；`SIPUpstream.transport` 为空默认 UDP，可显式选择 TCP 或 TLS 并复用持久连接完成 Digest、心跳和后续级联信令。出向 TLS 默认校验系统 CA，可配置独立 CA、服务端名称和客户端证书/私钥；入向 SIP-TLS 可配置客户端 CA，并可强制拒绝无证书或不受信任证书，实现传输层双向 TLS。上级注册的入站身份匹配、主动报警分发、可用上级枚举和状态 API 同时检查 `Registered` 与 `ExpiresAt`；刷新请求即使阻塞越过到期边界，也不能继续接受或向该上级发送业务，状态明确显示为 `expired`。2022 注册支持 301/302 的 UDP/TCP/TLS 与 `sips:` 重定向，并拒绝从 SIPS 降级到明文传输。Catalog 查询/订阅支持平台根、单个共享通道，以及共享目录图中可见的 2/4/6/8 位行政区划、系统、业务分组、虚拟组织和父设备范围；目录图只从显式共享项的 `CivilCode`、`ParentID`、`BusinessGroupID` 与来源系统关系递归加载或最小合成，查询目标必须真实存在于该可见图中，其他事件仍只允许已共享目标。目录通知按 2011 `Response`、2014+ `Notify` 根发送 ADD/DEL/ON/OFF/UPDATE 增量；分包使用相同 SN 和相同 `SumNum` 总数，`DeviceList Num` 仅表示当前分包条数。2014+ 域间目录订阅严格要求 `Event: Catalog;id=num`；`id` 是 RFC 3265 订阅对话内独立、稳定的数字事件参数，不等于消息体 `DeviceID`，并在续订、取消和 NOTIFY 中原样复用。2011 继续使用旧 `presence` 事件。上级事件订阅会自动建立、续订、复用和取消真实下级订阅。上级订阅对话与下级引用表均按订阅键串行网络操作，无关设备/事件可并行；在途创建使用占位状态，关闭会等待它收敛后再退订，不会遗留刚创建的下级订阅；批量建立中后续项因调用方取消失败时，回滚会脱离该取消信号并保留原身份路由，真正退订此前已建立的下级会话。级联 DeviceConfig/有业务应答 DeviceControl 的生产默认函数已通过真实 TCP `MESSAGE → SIP 200 → 业务 Response` 串联测试；无业务应答 DeviceControl 覆盖 `MESSAGE → SIP 200`。两条路径均覆盖动态 SN、真实/暴露编码、四版本 `X-GB-Ver`、`Monitor-User-Identity` 和 pending 清理。事件 NOTIFY 使用独立串行锁与上级 worker 生命周期 context，热更新或关闭上级时不会被在途 NOTIFY 响应等待阻塞；真实平台互通和生产验收仍需单独排期。
- 设备删除时的出向订阅清理已补齐：成功订阅保存原 XML 详细参数；删除仍在线设备时在原对话发送 `SUBSCRIBE + Expires: 0`，并立即释放本地索引。发送或确认失败不阻塞设备删除，离线设备、已消失通道和缺少完整旧对话的运行态只做本地清理。
- 注销/超时离线会同步清理该设备出向订阅对话，避免重注册后复用旧 Call-ID/tag；级联引用保留以支持目录收敛后重建。过期清理改为对话对象条件删除，不会误删 terminated 重建或并发续订的新对话；四版本共用的订阅判断统一在 `now >= ExpiresAt` 时立即失效，边界时刻不再继续分发事件，并立即释放级联下级引用。2014/2016/2022 Catalog 未显式配置 Expires 时按对应域间目录订阅附录默认 600 秒，2011 和其他事件继续使用 3600 秒；显式出向 Expires 保持可配置，但统一限制在 Owl SIP 解析器的 `uint32` delta-seconds 范围内，避免本地计时溢出或对端回显后无法解析。
- 出向订阅同时按版本引用的 RFC 3265/6665 处理 `Subscription-State` 参数：active/pending NOTIFY 的合法 `expires` 是事件源报告的权威剩余期限，可缩短但不能延长本地订阅；期限会与早于 SUBSCRIBE 最终响应到达的首个 NOTIFY 收敛，并同步提前刷新级联下级订阅。terminated 的 `reason/retry-after` 已进入级联重订策略：`timeout/deactivated` 可立即重订，`probation/giveup`、未知扩展原因及未携带原因时按适用的 `retry-after` 延迟，`probation` 缺省退避 5 秒，`rejected/noresource` 禁止自动重订；2022 对 RFC 6665 新增的 `invariant` 同样禁止重订，旧三版仍按 RFC 3265 未知扩展原因兼容。上级续订不能绕过等待期。畸形、重复、负数、引号或溢出的已知参数返回 SIP 400 且不删除原对话，未知通用扩展参数保持兼容。入向 NOTIFY 缺失、空值或重复 `Event` 时返回 `400`，不支持的事件包返回 `489 Bad Event`，已支持但不匹配订阅对话的事件保持返回 `481`；事件类型及 `id` 按 RFC 逐字节匹配，其他通用参数不参与对话匹配，所有拒绝路径均不修改原对话。事件源发送 NOTIFY 后也按版本处理失败响应：2011/2014/2016 的 `481` 和无合法单值 `Retry-After`、且无 401/407 认证后续动作的其他确定错误删除软状态；2022 仅对 RFC 6665 列出的 `404/405/410/416/480–485/489/501/604` 删除，500/503 等保留。未重复携带 `X-GB-Ver` 的上级订阅会保存协商版本，避免后续 NOTIFY 退回 2011 档案。

### 2.2 当前实现状态（2026-08-29）

- 四版本出向直播、回放/下载、语音及级联语音 INVITE 均接受全部 `200–299` 成功响应并先 ACK 后校验 SDP；同一 To-tag 对话重传 2xx 会原样重发缓存 ACK，非 2xx 最终响应自动 ACK，调用方取消后保留原事务完成 `CANCEL/487/ACK`。
- 四版本共用的入向 INVITE 对话确认已要求最终响应分配的非空 To-tag；最终响应前提前到达的无 tag ACK 不再建立广播或级联媒体会话，并由 `TestInboundInviteDialogRejectsACKBeforeFinalResponse` 覆盖 `1.0/1.1/2.0/3.0` 矩阵。

- `1.0/1.1/2.0/3.0` 共用同一套版本协商、能力门禁、SIP/XML/SDP 和设备模型；不需要拆分独立项目。附录 I 要求 REGISTER 的成功和失败响应均携带 `X-GB-Ver`，设备服务端对 200/401/403 等响应统一声明平台 3.0；级联客户端会从认证 401 起单调降级并用已获知版本发送带 Authorization 的下一次 REGISTER，不再等最终 2xx 才降级。
- 四版本 Catalog 查询的可选 `StartTime/EndTime` 已贯通统一查询 API 和级联：出站按北京时间编码已设置边界，入站先校验时间再按通道增加时间闭区间过滤；2014/2016/2022 对匹配的显式共享通道继续补齐可见目录祖先。无时间边界时保持原目录结果，避免影响既有调用方。
- 2011/2014 代码能力已完成自动化和本地模拟器覆盖，但真实设备矩阵、目标环境灰度和正式检测认证仍未完成。
- 2022 附录 H/J 目录路径已复用现有 `channels + Ext.GBCatalog` 快照实现：Catalog 首项输出无 `ParentID` 的本平台系统目录项；围绕显式共享设备递归加载系统、行政区划、业务分组、虚拟组织和父设备节点，存储中缺失时只依据已确认的来源、父子、业务分组和 `CivilCode` 前缀关系补最小目录项。相同平台、目录或摄像机编码从多个直连下级上报时合并为单项，`ParentID` 汇总全部已确认的直接父节点，任一路在线则合并状态为在线。行政区划、系统、业务分组、虚拟组织和设备查询分别按附录 J 返回目标自身及允许的后代类型，任意合法编码但不在共享目录图中的目标会被拒绝。2014/2016 的附录 P 域间目录订阅复用同一白名单可见目录图，并按各自旧版字段档案输出；不生成 2022 独有的平台根目录项。收到 `X-PreferredPath` 后，直播、回放和下载按剩余路径的第一平台编码选择对应真实下级记录；该路径不可达时拒绝请求，不回退到另一条路径。2011 和使用非 200 类型本地编码的存量配置保持旧目录行为。
- 2011/2014/2016 附录 G 已完成静态身份、严格 XML、生产入向路由、GORM 存储、平台主动出向四类业务、进程重启在途恢复、限流、指标和审计查询的自动化闭环；默认发送器已用真实 TCP 覆盖 `MESSAGE → SIP 200 → 独立业务 Response → SIP 200`。明确未发出的主动请求只有在持久化关联删除成功后才移除内存关联，删除失败会保留内存状态并同时返回原错误和数据库错误，避免重启恢复静默残留。SIP MESSAGE 是 Owl 接入网关实现选择，不是附录 G 对传输方式的强制规定。真实外部系统互通、真实进程/数据库恢复演练及安全性能验收仍需单独执行。
- 四版本媒体 SDP 已同时支持 IPv4/IPv6：直播、回放、RTP 下载、2014 直接 TCP 下载、广播、对讲以及级联视频/语音会按地址生成 `IP4` 或 `IP6`，入向直接 TCP 地址继续执行同设备/CIDR、组播及链路本地安全检查；IPv4 报文字节保持兼容。
- 四版本普通直播的 `f` 字段保持完整结构但不再默认锁定 G.711：2011/2014/2016 可由设备选择 G.711、G.723.1、G.729、SVAC 或扩展 G.722.1，2022 再允许 AAC；级联视频应答优先透传下级实际媒体描述，缺失时使用完整空参数。广播/对讲仍按各版专用流程固定 PCMA/G.711。已核验 ZLMediaKit `master` 提交 `70bd146aa6320d6b0675aa10b5379deef8c3690b` 的 PS 解封装和重封装支持这些轨道；浏览器输出协议和播放器解码能力仍需逐编码实流验收，不以信令测试替代。
- 四版本平台主动 `INVITE` 的 2xx 应答统一先发送 ACK，再校验唯一 `Application/SDP`、非空且可解析的 SDP、目标媒体类型、传输协议、媒体方向、地址、端口及与 offer 一致的 SSRC；UDP 要求 `RTP/AVP`，被动/主动 RTP over TCP 分别要求 `TCP/RTP/AVP + setup:active/passive`。`rtpmap` 按完整负载编号解析并拒绝同一负载的冲突映射，避免第三方库前缀匹配或只取首项形成歧义；标准广播报文中 2014 使用 `96/PS/90000`、2016/2022 使用 `8/PCMA/8000`，显式且无冲突的厂商动态 PT 继续兼容。校验或主动连接失败时发送 BYE 并关闭 RTP 资源；2014 附录 O 裸 TCP 下载同样先 ACK，再校验 `m=video ... tcp`、负载 `96/PS/90000`、地址、文件大小和 SSRC，非法 2xx 不遗留已确认对话。设备 2xx 缺少 Contact 时直接按 RFC 3261 回退 To 作为远端目标，不再向响应补写本平台 Contact。2016/2022 的 `StreamMode=2` 校验成功后调用 ZLMediaKit `connectRtpServer`；向上级 `setup:passive` 端点发送级联 TCP 媒体时同样由 ZLMediaKit 作为客户端连接。2022 按附录 D 在上述 TCP 媒体客户端首次连接失败后至少重连 3 次，每次间隔不少于 1 秒，并响应调用方取消；控制接口返回空响应或级联发送返回非法本地端口也按本次建链不可用处理，不会绕过重连。2016 保持单次连接语义。LALMAX 当前公开实现没有主动 TCP 连接能力，因此在发送 INVITE 前明确拒绝该模式。
- 出站直播、回放、下载和广播/对讲 `INVITE` 的 `Subject` 接收方媒体流序列号复用当前会话的发送方序列号，不再固定为 `0`；发送方序列号由实时/历史 SSRC 生成，使同一接收端的并发媒体会话保持不重复，并覆盖实时与历史序列自动化测试。
- 入站级联视频及广播 `INVITE` 从 2014 起必须携带唯一 `Subject` 头域；2011 继续兼容未携带 `Subject` 的旧设备。出现 `Subject` 时要求四段式格式，校验双方 20 位国标编码、发送序列 `1..20` 字符、非空接收序列及当前媒体会话身份。级联直播发送序列首位必须为 `0`，回放/下载必须为 `1`；广播音频不套用视频首位规则。缺失或非法 `Subject` 在创建对话和启动 RTP 前返回 `400`。

- 历史控制倒放边界已细化：四版本均允许负 `Scale` 从当前位置倒放；2011 继续允许规范中的 `Scale + npt Range`，结构化倍速控制可携带起点，随机拖放使用 `smpte`；2014/2016 的快慢进只发送 `Scale`，随机拖放只发送 `Range`；2022 负 `Scale` 可与 `Range` 组合从指定位置倒放，有界倒放只接受结束点小于起点的降序范围，普通播放及旧版本仍拒绝降序范围。2022 仅携带 `Range` 时按 B.2.8 沿用该历史会话最近一次成功生效的 `Scale`：直连/下级媒体会话与每个上级对话分别保存倍率，只有下游业务成功才提交；因此负倍率后的降序 Range 可继续倒放，方向与已记录倍率冲突的范围会被拒绝。`RTP-Info` 的 `url/seq/rtptime` 按可选参数处理，允许只出现任一已知参数，但拒绝空条目、未知参数和重复参数。管理端回放控制已开放负倍率，并分别在 2011 倍速控制、2022 负倍率倒放时显示可选播放起点。
- 2022 级联升级与抓拍已形成发起、业务应答和最终通知闭环：每个上级任务把上级 `SessionID` 映射为独立下级会话号，避免多上级碰撞；相同会话和载荷的并发/迟到重传复用首次下发结果，不会重复启动设备任务，相同会话改载荷会被拒绝。直连和级联下游任务在命令下发前把目标、`SessionID`、状态及升级/抓拍元数据写入独立 `gb_task_states` 表；级联同时把上下级会话、原上级平台、真实/暴露通道、请求指纹、`Monitor-User-Identity` 和网关上下文写入 `gb_cascade_task_routes` 表，进程重启后可分别按上下游会话懒恢复。未完成路由恢复时重新核验当前上级协议版本、共享通道映射和身份授权；已完成路由作为持久化幂等记录，即使上级配置已删除也只确认下级重复最终通知，不会再次上送。`DeviceUpgradeResult`、`UploadSnapShotFinished` 必须关联原请求，未知会话不再由通知自行建档；最终通知只回送原发起上级，并重写通道编码、会话号和抓拍文件编码，且优先于迟到的业务应答。最终状态为单调不可逆：语义相同的重传保持首次状态和时间，矛盾结果返回 `409` 且不得覆盖；状态及级联结果必须先可靠持久化以决定 `200/5xx`，SIP ACK 写失败时保留终态等待重传。上级已确认最终通知而完成墓碑落库失败时，只重试墓碑持久化，不再次发送业务通知。升级结果、抓拍完成和 `VideoUploadNotify` 均是独立 MANSCDP 通知，只允许由 SIP `MESSAGE` 承载，不得注册为 RFC 6665 `NOTIFY`；三类正文按附录 A 的顺序、出现次数和嵌套结构严格校验，拒绝重复单例、未知节点、属性/命名空间、嵌套简单字段和额外 XML 指令，同时兼容报文开头的标准 XML 声明。非法 `VideoUploadNotify` 不写查询/A.4 状态，也不启动级联；合法通知只转发给 3.0、已注册且实际共享该通道的上级。任务状态与路由按 7 天和 1024 条上限回收，并随设备删除清理；删除入口向事务存储传递已解析的完整设备，不依赖数据库的 `DELETE ... RETURNING` 回填设备编码。自动化已覆盖进程重启恢复和二次重启去重，真实上级/设备重启互通仍需执行。

- SIP/TCP 采用有界逐行读取：单头行 8 KiB、总头 64 KiB、SIP 正文 1 MiB；UDP 解析使用相同正文上限，并要求 `Content-Length` 与数据报正文精确一致。超限/重复长度、截断正文和声明零长度后的尾随正文在分配或业务分派前拒绝；2014 附录 O 的文件数据使用独立裸 TCP 链路，不受 SIP XML 正文上限影响。
- 普通设备的 `MESSAGE/NOTIFY/SUBSCRIBE` 在业务路由前先确认当前注册运行态；完全未知或仅有历史建档但尚未恢复注册的设备返回 `403`，运行态存储不可用返回 `503`，且不能以“正文目标等于 From 编码”绕过检查并写状态、解除等待、触发回调或级联转发。直连设备入向 SUBSCRIBE 的能力门禁和响应格式只采用已注册运行态版本，忽略该次请求自报的 `X-GB-Ver`；级联则采用已鉴权上级的协商版本，避免低版本端伪造 3.0 开启 `MobilePosition`/`PTZPosition`。这样也避免没有运行档案时把 2014/2016/2022 业务误按默认 2011 解析。附录 G 外部系统和已注册上级平台仍走各自身份门禁。Keepalive 在 XML 解析后使用更窄的恢复例外：当前运行态或持久化建档任一存在即可通过，保证重启恢复，同时直接 handler 路径也不会创建完全未知运行态、写查询状态或触发 Catalog；合法设备只有在 `200 OK` 实际写出成功后才提交内存态，然后执行设备/历史持久化、订阅 NOTIFY 转发和首次 Catalog 补载；省略 `Status` 的兼容心跳在结构化状态与持久状态中均一致视为在线。Alarm、MobilePosition、DeviceInfo、DeviceConfig、ConfigDownload 及通用查询响应同样先完成候选解析，确认入向 SIP 报文后再更新内存快照、解除查询等待，并执行各自 Schema 允许的数据库写入、外部回调和订阅转发；同一通用查询报文只解析和持久化一次，后续状态更新直接复用首次版本校验后的 A.4 结果，即使处理期间设备运行态消失也不会按 2011 回退重解码并丢失 2022 扩展。慢数据库、订阅方、业务回调或目录超时不再拖延设备确认、触发重传或造成心跳误离线。
- 附录 A.4“联网系统扩展应用”是 2022 新增能力；Alarm、DeviceConfig、DeviceInfo、DeviceStatus、ConfigDownload 和 Catalog 等公开入站入口在状态更新、目录聚合、等待解除、数据库持久化、业务回调及订阅转发前统一识别 A.4 对象。2011/2014/2016 携带 `doorType`、`detectorType` 或 `ExtraInfo/ExtralInfo` 等 A.4 扩展时返回 `400` 且不产生副作用；通用解码层仅为 2022 设备保存其命令 Schema 允许的 A.4 对象，作为遗漏入口的防御门禁。`ExtraInfo` 按 Schema 的普通 `string` 在 A.4 快照、录像响应重建和 Catalog 级联提取中保留首尾空白；JSON 解析仅用于结构化识别，不改变保存的原始值。MobilePosition 的 2016/2022 Schema 均未定义 `Info`、`ExtraInfo/ExtralInfo` 或 A.4 对象，四版本入口一律在状态与转发前拒绝。
- 通用查询严格区分 SIP 方法和 XML 根：`MESSAGE` 查询应答只接受 `Response`，订阅 `NOTIFY` 事件只接受 `Notify`；两者均校验正 `SN`、命令类型、版本能力和目标所有权。上级入向级联 Query 还在返回 SIP `200` 和启动异步转发前按命令校验标准字段顺序、单例、属性/命名空间和简单字段结构，拒绝未知字段及跨命令载荷。合法事件通知可以更新状态和转发订阅，但不能解除 `MESSAGE` 查询等待；2022 `VideoUploadNotify` 等独立业务通知仍按其专用包络处理，不套用查询应答矩阵。未知跨设备编码不能产生任何副作用。出向订阅收到非空 `NOTIFY` 时，订阅中间件只执行无副作用的对话、Event、Subscription-State 和 CSeq 候选匹配；只有 Catalog、Alarm、MobilePosition 或 PTZPosition 正文完成版本、结构、业务值和目标校验后，才提交远端 tag、CSeq、有效期或 terminated 删除，非法正文不能提前占用 CSeq 或终止订阅。预置位查询内部统一为 `PresetQuery`；2014 出站设备查询及级联响应按修改补充文件编码为 `PersetQuery`，入站兼容两种拼写，2016/2022 出站使用已修正的 `PresetQuery`。
- 统一设备查询不接受 `action=broadcast`：标准中的语音广播不是附录 A.2.4 查询，而是 2014+ 规定的 `Notify/Broadcast`、独立 `Response/Broadcast` 及接收者主动 INVITE 流程；调用方应使用语音广播 API，避免发送非标准 `Query/Broadcast` 后等待无法关联的响应。
- 通用查询 NOTIFY 路由只保留 2022 `PTZPosition` 事件；DeviceStatus、Preset/HomePosition/CruiseTrack/SDCardStatus/ConfigDownload 等查询或状态命令只作为 `MESSAGE + Response` 处理，不能由 `NOTIFY` 写状态或转发为订阅事件。查询应答也不再调用事件发布链路。
- 通用查询在产生状态、解除等待或转发订阅前校验业务载荷：DeviceStatus、PresetQuery、HomePositionQuery、CruiseTrackListQuery、CruiseTrackQuery、PTZPosition 和 SDCardStatus 均按版本固定顶层顺序、单例次数、列表 `Num` 属性和内部字段结构，拒绝重复/未知字段、属性/命名空间、简单字段嵌套和乱序；预置位、巡航轨迹和存储卡的必填字段及列表计数必须一致，看守位开关和预置位范围、巡航编号/名称/速度、PTZ 有限浮点数、存储卡状态/进度/容量均按标准约束。2014/2016 的预置位应答不要求 2022 新增的 `SumNum`，并受控兼容存量设备在 `PresetList` 前附带单例 `Result`、`SumNum`，但结果枚举、位置及计数仍必须合法。
- DeviceInfo 四版本应答复用通用包络和目标所有权校验，并额外约束固定命令；非法应答不能覆盖父设备/子通道信息或唤醒查询等待。尾部基本扩展按 2011/2014/2016 纯文本 `Info`、2022 纯文本 `ExtraInfo` 的精确矩阵校验，单项最长 1024 个 Unicode 字符；2022 结构化 `<Info>` 仅作为已识别附录 A.4 对象的承载容器接受。
- DeviceInfo 四版本均按标准要求固定 `Response` 根和必填 `OK/ERROR` 结果，空 Result 不再被当作成功后覆盖设备/通道元数据；DeviceControl、Broadcast、Upgrade、Snapshot 和 ConfigDownload 的公开等待路径也不再保留空结果成功兜底，防止内部或未来入口绕过协议校验。
- DeviceStatus 四版本应答按标准校验固定字段顺序和单例结构，以及必填的 `Result=OK/ERROR`、`Online=ONLINE/OFFLINE` 和 `Status=OK/ERROR`；可选 `Encode/Record` 仅允许 `ON/OFF`，`DeviceTime` 出现时必须为合法 `dateTime`。`Alarmstatus` 校验版本化计数属性、条目结构、20 位设备编码和 `ONDUTY/OFFDUTY/ALARM` 枚举；2011 兼容其 Schema 的 `Status` 与正文/示例的 `DutyStatus`，2014 修改补充文件优先使用修订字段 `StatusDutyStatus`，同时兼容存量设备的 `DutyStatus`，2016/2022 使用 `DutyStatus`。非法结构、失败结果及子通道状态不再改写父设备在线运行态。四版均把该消息定义为状态查询应答，没有规定 `Online=OFFLINE` 等同 REGISTER 注销或必须终止媒体；因此它只更新同一有效注册绑定内的可恢复在线状态。设备或通道状态落库失败时保留最后已提交运行态并登记待补偿值，周期扫描在统一设备活动锁内重试；新 REGISTER、注销、Keepalive 或更新的 DeviceStatus 会清除或覆盖旧补偿，迟到重试不能反压新绑定。持久化档案使用可缺省的 `gb_registration_closed` 区分绑定关闭与状态离线：升级前缺失该字段时继续按原 `IsOnline` 行为处理，写入新状态后可在进程重启时恢复有效离线绑定；入向状态报送按有效 REGISTER 放行，主动查询/控制仍要求设备当前在线，离线绑定到期后照常关闭。
- DeviceStatus 尾部基本扩展字段按版本保留：2011/2014/2016 使用可多项的纯文本 `Info`，2022 使用可多项的纯文本 `ExtraInfo`，每项最长 1024 个 Unicode 字符；跨版本字段拒绝。`Reason`、纯文本 `Info/ExtraInfo` 按 Schema 普通 `string` 原样保存首尾空白，枚举、设备编码和日期时间仍规范化。2022 原始 `ExtraInfo` 同时保留在结构化状态中，并继续进入附录 A.4 对象解析与持久化流程；2022 的结构化 `<Info>` 仅作为附录 A.4 已识别对象的承载容器接受，不混入旧版 `Info` 状态。旧版下级向 2022 上级级联时，纯文本 `Info` 会转换为 2022 的 `ExtraInfo`，避免透传出版本不合法报文。
- DeviceControl 按四版本标准区分有无业务应答：PTZ、TeleBoot、DragZoom、IFrame 及 2022 PTZPrecise/FormatSDCard/TargetTrack 只等待 SIP `200 OK`；Record/Guard/AlarmReset/HomePosition/DeviceUpgrade/DeviceConfig 等继续等待业务 Response。2011 规范性附录 J.6 的 PTZ `Info/ControlPriority` 已贯通统一接口与 XML，2014 修改补充文件继续沿用；只允许 1.0/1.1 直连和旧版间级联，跨到 2.0/3.0、脱离 PTZCmd 或与报警复位 Info 混用时拒绝。强制关键帧严格按 2016 标准原文的 `IFameCmd` 与 2022 的 `IFrameCmd` 编解码，级联跨版本时转换字段名，错误版本字段和两字段并存均拒绝，2011/2014 继续由能力门禁拒绝。统一接口的 `ptz_cmd` 支持动作名编码及兼容 16 位原始 PTZCmd，原始命令校验 `A5 0F` 头和校验和；公开动作列表已与真实的 start/stop、set/reset 动作名同步，历史动作别名 `ifame_cmd` 兼容映射为 `iframe_send`。级联无应答命令不会登记 pending 或向上级伪造 `Response/DeviceControl`；入向级联在 SIP `200` 前完成完整版本、参数和能力校验，非法请求直接返回 `400`。2022 `PTZCmdParams` 必须伴随 PTZCmd、上下游均为 3.0，`PresetName` 仅允许设置预置位命令，`CruiseTrackName` 仅允许巡航命令且按原始出站值限制为最长 32 字节，两者不能同时出现；名称首尾空白作为普通 `string` 内容原样下发，仅全空白值视为未提供。2016/2022 `HomePosition` 在 `Enabled=0` 时拒绝仅供开启看守位使用的 `ResetTime/PresetIndex`。设备迟到或额外发送的合法 Response 仍以 SIP `200` 兼容确认；有应答 DeviceControl 及 Broadcast 2014+ 应答校验 `Response` 根、固定命令、正 SN、必填结果枚举和目标所有权，响应目标还须与对应在途请求一致，非法应答不能解除等待。
- DeviceControl 录像码流字段按精确版本矩阵编码：2011/2014/2016 均不输出 `StreamNumber`；2022 接受任意非负整数（0 主码流，1/2/... 子码流），缺省 0 省略。级联只接受 2022 上级携带该字段，非零值仅能转发给 2022 下级，零值跨到旧版时按相同缺省语义裁剪。
- 级联 DeviceControl 从属字段不会再脱离主命令通过校验：`StreamNumber` 必须属于 `RecordCmd`，报警 `Info` 必须属于 `AlarmCmd`，2011/2014 `ControlPriority` 必须属于 `PTZCmd`，`DeviceID2/TargetArea` 必须属于 `TargetTrack`；非法组合在 SIP `200` 前返回 `400`。
- DeviceControl 尾部普通文本扩展已贯通 HTTP/Core/Adapter、直连设备和四版本双向级联，下发时保留首尾空白、空值和 XML 转义，并限制单项最多 1024 个 Unicode 字符；2011/2014/2016 编码为多项 `Info`，2022 编码为多项 `ExtraInfo`，跨版本自动按目标版本改名。级联入站在 SIP `200` 前严格校验 `Control` 根、核心包络、动作及从属字段顺序/单例、复杂参数必填子字段、属性/命名空间和未知节点，并区分结构化报警复位 `Info` 与普通文本扩展。
- Keepalive 四版本在补载设备和写在线态前校验 `Notify` 根、固定命令、正 SN、源设备一致性及故障设备编码；标准 `OK/ERROR` 外继续兼容已记录的空值、`ON/OFF` 厂商状态。
- Keepalive 按四版本共同的周期状态报送语义先完成无副作用的解析、身份和注册绑定校验；只有 SIP `200 OK` 实际写出成功后，才创建/更新运行态、结构化查询状态，并持久化在线状态、心跳时间、来源地址、信令传输和协议版本。写失败时保留原状态供同事务重传，避免重启补载产生半初始化设备。持久化失败时不会丢弃已经确认的设备活动：运行态采用本次心跳、当前连接和来源，并登记同一 REGISTER 代次的待补偿观测；离线扫描恢复后补写数据库。新的 REGISTER、注销/超时关闭、更新的 DeviceStatus、成功 OPTIONS 或更新的 Keepalive 会清除或替换旧补偿，迟到重试不能覆盖新注册或更新状态；OPTIONS 成功使用同一观测时间同步持久态和运行态，并显式恢复在线标记。
- Alarm 四版本在附录 A.4、业务回调和订阅转发前校验 `Notify` 根、固定命令、正 SN、目标所有权、报警级别/方式/时间及有限经纬度；普通 `string` 字段 `AlarmDescription` 原样保留首尾空白，报警级别、方式、类型、时间和坐标仍规范化。2011/2014 仅接受可多项、单项最长 1024 个 Unicode 字符的纯文本 `Info`，拒绝 2016 才新增的结构化 `AlarmType` 和 `AlarmTypeParam/EventType`；2016 最多接受一个结构化报警类型 `Info`，出现时 `AlarmType` 必填且必须位于可多项纯文本 `Info` 之前，结构化节点与纯文本不能混用；2022 将纯文本扩展改为多项 `ExtraInfo`，并只允许最多一个结构化 `Info` 承载报警类型和已识别的附录 A.4 对象。级联按上级版本转换纯文本 `Info/ExtraInfo`，2011/2014 裁剪结构化报警类型和附录 A.4，2016 保留可表达的纯文本扩展并裁剪附录 A.4；2022 的 `AlarmMethod=5/AlarmType=13` 降级到 2016 时会移除该版本无法表达的结构化类型字段，但保留基础报警和普通文本扩展。2016/2022 按报警方式校验报警类型，并仅允许入侵检测报警携带 1/2 事件类型；非法报警不产生任何业务副作用。合法 `MESSAGE/Notify/Alarm` 先返回标准要求的空正文 SIP `200 OK`，再向报警源发送相同 SN、报警目标及 `Result=OK` 的独立 `MESSAGE/Response/Alarm`，并异步等待对端 SIP 确认；订阅产生的 `NOTIFY/Alarm` 仅返回 SIP `200 OK`，不会误发第二条业务应答。
- 2022 Alarm 的结构化 `Info` 仍是最多一个节点；报警类型与附录 A.4 对象需要在同一 `Info` 内组合，纯文本扩展使用可多项的 `ExtraInfo`。向 2016 降级时保留合法报警类型并裁剪同节点内的 A.4 对象，第二个 `Info` 在任何副作用前拒绝。
- MediaStatus 按 2011 第 9 章流程和附录 J 对四版本开放，并校验 `Notify` 根、固定命令、正 SN、必填设备与通知类型；可找到会话现场时强绑定父设备/通道和 Call-ID。未知通知类型及已清理会话的重复 `121` 保持幂等确认，非法目标不能结束媒体任务。
- RecordInfo 四版本标准共有的 `FilePath`、`Address`、`Secrecy`、`RecorderID` 已从通道录像 API 和统一 GB A.2.4 查询 API 贯通到核心端口、GB 适配器、设备 SIP XML 与平台级联；`FilePath`、`Address`、`RecorderID` 按四版 Schema 的普通 `string` 处理，不限制 `RecorderID` 为 20 位设备编码，也不裁剪普通字符串的首尾空白，并覆盖 XML 转义、中心录像精确过滤、四版本门禁与级联原值保留；两套公开入口的核心层均不再提前套用 2016/2022 的必填时间规则，2011/2014 省略 `StartTime/EndTime` 可实际下沉到协议层，2016/2022 仍由版本门禁拒绝缺失时间。统一 GB A.2.4 查询入口的 `target_id` 省略或等于已注册设备编码时，现按设备/系统级 RecordInfo 复用该设备当前注册连接发送，SIP Request-URI、`To` URI 和 XML `DeviceID` 均使用设备/系统编码；通道目标继续沿用原通道路由。四版本线级测试覆盖设备/系统目标，2014/2016/2022 同时验证 `IndistinctQuery=0` 的位置选择字段不被裁剪；公开请求模型、Swagger 和核心/映射测试同步覆盖。

- 同一设备的 REGISTER 查询、鉴权、首次自动建档和状态提交按设备串行，不同设备互不阻塞；多实例并发首次建档发生唯一键竞争时回读已创建记录，UDP 重传或并发 REGISTER 不再因重复建档误回 `500`。完全相同且同源的成功事务重传在有界短期缓存中复用原 `200/Date`，不重复写注册历史或触发 DeviceInfo/Catalog；认证头、Expires、源地址等发生变化时仍按新请求处理。
- SIP/TCP/TLS 长连接空闲等待首字节不设置超时，兼容低频心跳；一旦收到首字节，完整 SIP 头和正文必须在 30 秒内读完，超时关闭连接，避免慢速逐字节请求长期占用 goroutine。
- XML 的 UTF-8→GBK/GB18030 厂商兼容回退改为临时对象原子解码：首轮失败时不会把已解析的部分目录/录像切片留在目标中，第二轮成功不会产生重复项，两轮均失败也不会污染调用方已有状态。
- 省略显式 `Sip.Domain` 时，REGISTER 和 MESSAGE/NOTIFY Digest 挑战、验签以及回放响应补写的 Contact 均统一使用平台 ID 前 10 位派生域。两类 Digest 验签都会在计算前保存客户端原始 `response`，拒绝错误口令；兼容 MESSAGE/NOTIFY Digest 还绑定 realm、username、请求 URI、方法、设备和源 IP，并通过有界、限时 nonce 与递增 `nc` 防止跨请求重放。
- SIP 配置启动加载和 API 更新统一校验 20 位平台 ID、10 位有效域、端口、TLS 必填项、设备历史范围、信令摘要及上级 `Monitor-User-Identity` 身份/授权策略。API 先原子写盘再提交运行时快照，写入失败不会污染内存；Host、平台 ID/域、监听端口、TLS 和 SIP 报文日志等需要重建监听器、身份或全局日志器的字段明确要求修改文件后重启，其余鉴权、摘要、历史、2014 直连下载和上级级联配置使用并发安全快照热更新。
- SIP UDP/TCP/TLS 在应用构建阶段同步绑定并显式返回地址、证书或端口占用错误，持久化设备/通道恢复错误也沿构建链路返回，不再由后台 goroutine 或缓存加载 `panic`；部分启动成功后的监听器会统一回收。UDP 设备恢复完成后立即执行一次 REGISTER 到期扫描，再启动周期任务，避免服务启动后最长 60 秒仍把过期设备和通道显示为在线。设备离线检查也随 GB28181 服务生命周期停止，避免停服后遗留永久定时 goroutine。
- Catalog 完整快照会先校验全部目录/通道目标可安全构造 SIP URI，发现控制字符或空目标时拒绝整份快照而不是部分覆盖，同时保留安全的厂商非标准编码兼容；持久化恢复与统一出站请求入口还会校验目标连接和目的地址，避免畸形厂商目录在后续点播或查询时触发空指针。
- 在线设备的注册、心跳、连接、地址、口令和离线时间统一由受锁运行态维护；同一设备的数据库更新与运行态同步作为一个串行操作提交，OPTIONS 只有在设备返回 `200` 且活动时间成功提交后才算探测成功。REGISTER 鉴权和绑定状态先可靠提交，再写出 SIP `200`；只有响应实际成功后才缓存应用层幂等结果、增加成功指标、记录注册历史并启动 DeviceInfo、Catalog、ConfigDownload 查询，写失败时同请求重传重新完成确认，不能因提前缓存而漏掉初始化。离线扫描独立检查 `RegisteredAt + Expires`：注册绑定在到期边界立即失效，近期 Keepalive 或 TCP/TLS OPTIONS 可达性不能代替 REGISTER 续期。普通 MESSAGE/NOTIFY/SUBSCRIBE 的统一门禁、Keepalive 的持久设备恢复入口，以及平台主动查询、控制、点播、订阅、升级、抓拍、语音和 OPTIONS 的公共在线判断均使用同一绑定语义，已注销、已离线或已过期设备不能在扫描间隙继续业务或被心跳重新写成在线；升级前缺少绑定时间元数据但仍明确在线的存量记录保持兼容。REGISTER、Keepalive、OPTIONS 活动提交、DeviceStatus 在线状态和离线扫描使用同一设备活动锁；旧离线清理必须在锁内完成，不能删除新 REGISTER 建立的查询、订阅或媒体。设备/通道离线持久化任一步失败时，运行态立即关闭注册绑定并释放旧业务资源，同时保留待补偿标记由后续扫描重试；DeviceStatus 的临时 `OFFLINE → ONLINE` 恢复与 REGISTER 注销/超时明确区分，迟到状态包不能重新开启已关闭绑定。2014+ 广播接收者主动 INVITE 还必须来自当前有效注册设备，未授权的畸形请求不能终止待建广播会话；设备对平台主动媒体会话发送 BYE 时除设备编码、Call-ID 和对话 tag 外，还需匹配原 2xx 响应来源 IP。扫描在落库前复核注册/心跳代次，旧扫描不能覆盖刚完成的 REGISTER、Keepalive 或 OPTIONS 探测。服务重启恢复设备时同步恢复注册 `Expires`。媒体、查询、控制、摘要和级联调用读取一致快照，出站请求一次取得同代 To/连接/目的地址，避免重注册和并发心跳期间的数据竞争或跨连接组包。
- REGISTER 成功结果缓存最长 1 分钟，但 2011 兼容的短注册周期会把缓存同步缩短到绑定有效期；设备口令编辑使旧绑定失效时也同步删除该设备的成功缓存，旧鉴权报文不能再绕过新凭据返回伪成功。
- SIP 报文日志器只在所有监听器启动成功后切换；并发报文写入与关闭使用同一互斥锁，启动回滚和停服不会关闭仍在写入的输出对象。
- RTP 下载终态、2014 裸 TCP 下载终态和设备结构化查询快照均增加 TTL 与容量上限；小时清理器随 GB28181 生命周期退出，无新任务时也能回收过期状态和文件，活动下载及其 `.part` 文件不会被误删。GB28181 服务关闭时会永久关闭 2014 裸 TCP 下载管理器，取消并等待活动下载及其连接取消 watcher 全部退出，关闭后拒绝新下载。结构化查询读取及 `DeviceQuery` 返回值均包含嵌套切片、指针和 A.4 字段映射的深快照，诊断/API/SDK 调用方不能改写内部运行态，也不会与后续报文合并产生数据竞争。
- 服务关闭会幂等释放普通直播、回放/下载、广播、对讲和级联媒体资源；直播/历史 RTP 端口打开失败或主动停止半初始化会话时不会遗留占位流或 RTP 接收端口，即使设备 2xx 畸形无法构造 BYE 也继续完成媒体端清理。媒体服务器报告普通直播、回放或 RTP 下载流注销/超时时，会先原子删除流，再向直接下级设备发送会话内 `BYE`、关闭 RTP 接收端口，并继续向引用该源的上级级联会话发送 `BYE`；重复注销不会重复信令或清理。级联语音源在等待媒体期间收到上级 BYE、媒体注销或上级 worker 终止时会立即打断等待并关闭接收端口；终止标记与下游广播索引绑定共用同一状态锁，终止前已绑定的会话会被完整停止，终止后不能重新挂接。MediaStatus `NotifyType=121` 和普通出站媒体的入向 BYE 均先定位并保留候选会话，只有 SIP `200 OK` 实际写出成功后才原子删除会话并设置终态；媒体服务器关端口、下载进度刷新和播放状态写库继续放在确认之后，慢外部清理不导致重传，确认写失败也不会制造假终态。级联 INVITE 清理器只回收长期未建立的半开会话，已建立的长时直播/回放不再因 10 分钟没有 SIP 控制消息而被误切断。
- 服务关闭会立即取消 PTZ、设备控制/查询/配置、升级、抓拍、广播、级联媒体/语音和 Catalog/RecordInfo 等业务等待，清空在途请求、响应别名及订阅索引，并禁止继续创建出站 SIP 请求，不再依赖各业务 6～10 秒超时自行退出。仅等待 SIP 最终响应的无业务应答 DeviceControl、MobilePosition Query、独立 PTZ、TimeSync、OPTIONS、出向 SUBSCRIBE 及级联无应答控制也进入统一在途设备请求表；删除设备、注销/离线和单通道 Catalog 离线分别以 `ErrDeviceNotExist`、`ErrDeviceOffline`、`ErrChannelOffline` 立即收敛，其他设备及在线兄弟通道不受影响，清理后的迟到成功不会提交。全局 SIP 生命周期中间件将已经接纳的 REGISTER/MESSAGE/NOTIFY/SUBSCRIBE/INVITE 等请求纳入关闭等待，并从停服开始起拒绝新业务；关闭采用“停止接纳并取消业务 → 注销级联并关闭 SIP 以解除事务/连接等待 → 等待 handler → 清理 GB 会话索引”的两阶段顺序，避免清理后又写回运行态或在等待 handler 时互锁。上级级联广播、控制、查询、初始/增量目录 NOTIFY、terminated 订阅续订及设备 Catalog NOTIFY 后刷新统一纳入 GB28181 生命周期；关闭与任务接纳串行化，避免 `WaitGroup.Add`/`Wait` 竞态，关闭会取消并等待在途任务且拒绝新任务。级联 NOTIFY 同时继承调用方和上级 worker 的取消信号，不会绕过 30 秒调用超时或停服取消。
- Web/Adapter 传入的调用方 `context` 已贯通实时点播、历史回放/下载、控制、查询、配置、订阅、升级、抓拍和语音等 SIP 最终应答及业务等待；级联实时点播也将入向 INVITE 会话取消传播到下级点播，上级 CANCEL 后不再继续占用下级 SIP 事务和通道媒体锁。已取消请求不会继续发送命令，等待中取消会关闭对应事务并立即释放调用链，同时保留旧无 context 方法的向后兼容入口。
- 同一通道的直播、回放/下载、2014 直连下载、广播、对讲及停止操作保持串行，并支持 context 取消；锁由设备按通道 ID 引用计数管理，Catalog 替换通道对象时仍保持同一把锁，最后释放后自动删除。NVR 不同通道可并行，避免一个通道等待 SIP/媒体应答时阻塞整台设备。
- SIP 连接封装对空远端地址、非数据报底层连接及缺失出站连接/目的地址返回明确错误，不再通过类型断言或关闭错误包装触发 panic。

### 2.3 数字证书 REGISTER 配置边界

下级设备接入使用 `Sip.RegisterCertificateAuth`。`DeviceCertificates` 必须显式绑定 20 位设备国标编码，不能依赖证书 CN 猜测身份；`DeviceCA` 为空时固定信任映射证书，配置 `CRL` 时必须同时配置 `DeviceCA`。该运行态包含平台私钥、设备信任锚和 nonce 表，修改后必须重启：

```toml
[Sip.RegisterCertificateAuth]
Enabled = true
Required = false
PlatformCert = './configs/certs/platform.crt'
PlatformKey = './configs/certs/platform.key'
DeviceCA = './configs/certs/device-ca.crt'
CRL = './configs/certs/device.crl'

[Sip.RegisterCertificateAuth.DeviceCertificates]
'34020000001320000001' = './configs/certs/device-34020000001320000001.crt'
```

向上级平台注册在对应 `[[Sip.Upstreams]]` 下配置独立证书。`Required=true` 会隐式启用 Capability，并拒绝上级回落到 Digest 或未完成 Asymmetric 挑战就直接返回 200；该证书与 SIP-TLS 的 `TLSCert/TLSKey` 用途不同：

```toml
[Sip.Upstreams.RegisterCertificateAuth]
Enabled = true
Required = true
LocalCert = './configs/certs/cascade-local.crt'
LocalKey = './configs/certs/cascade-local.key'
ServerCert = './configs/certs/upstream.crt'
ServerCA = './configs/certs/upstream-ca.crt'
CRL = './configs/certs/upstream.crl'
```

### 2.4 Monitor-User-Identity 配置边界

2011、2016、2022 的 8.3 条款使用相同规则；2014 修改补充文件未修改该条款，继续沿用 2011。标准规定头值依次由一个或多个信令安全路由网关 ID、用户 ID、用户隶属机构、用户类别和用户职级组成，各段使用 `-` 分隔。因此属性值不得包含 `-` 或控制字符，网关 ID 必须是类型码 `211` 的 20 位编码，用户 ID 必须是类型码 `300-499` 的 20 位编码。

该策略按上级平台独立配置并支持热更新。`Required=true` 会隐式启用身份验证，并要求至少配置一项用户或属性白名单；直接上级网关同时与已注册上级平台的 SIP ID、源 IP 及 TLS 连接（如适用）绑定，不能仅凭头值获得信任：

```toml
[Sip.Upstreams.MonitorUserIdentity]
Enabled = true
Required = true
LocalGatewayID = '34020000002110000001'
RemoteGatewayID = '34030000002110000001'
LocalUserID = '34020000003000000001'
LocalOrganization = '340200'
LocalCategory = 'operator'
LocalRank = 'level1'
TrustedGatewayIDs = ['34040000002110000001']
AllowedUserIDs = ['34030000003000000001']
AllowedOrganizations = ['340300']
AllowedCategories = ['dispatcher']
AllowedRanks = ['level2']
MaxHops = 8
```

本域生成时使用配置的真实用户档案；转发外域身份时只在已验证的原值前添加本地网关 ID。系统拒绝重复头、非法分段、非 211 网关、非用户编码、不可信中间网关、重复网关、路由环、超跳和属性越权。应用层首先把直接网关绑定到已注册上级的 SIP ID、源 IP 及已验证 TLS 连接；使用 UDP/TCP 明文时仍应由部署网络提供标准要求的 IPsec 或等价可信边界，不能把源 IP 当作密码学身份证明。真实安全路由网关、用户目录及跨机构授权规则仍属于生产互通验收证据。

## 3. 当前实现基线和主要缺口

### 3.1 已有基础

- `pkg/gbs/sip` 已具备 SIP 消息、事务、UDP/TCP 监听、Digest 鉴权和 XML 编解码能力。
- `pkg/gbs` 已有注册、心跳、目录、设备信息、报警、录像、PTZ、语音、订阅和 INVITE 基础流程。
- 设备扩展数据已有 `GBVersion` 字段，数据库使用 JSON 扩展，不需要新增独立表。
- 2016/2022 已有部分版本门禁和 `X-GB-Ver` 下行发送逻辑。

### 3.2 必须先修复的问题

1. `pkg/gbs/sip/context.go` 只识别 `1.0/2.0/3.0`，缺少 `1.1`。
2. `pkg/gbs/catalog.go` 的 `wrapRequest` 没有 `1.1` 分支，未知版本默认发送 `3.0`，对老设备不安全。
3. 注册 `401`、`200` 和失败响应没有统一返回 `X-GB-Ver`。
4. 设备不携带版本头时，数据库版本可能被空值覆盖；内存默认版本和下行默认版本不一致。
5. 注册成功后无条件发送 `ConfigDownload`，纯 2011 设备可能不支持。
6. 目录模型缺失 2014 增加的 `ParentID`、`BusinessGroupID`、`IPAddress`、位置属性等字段。
7. 四版本共有的 `MediaStatus`，以及 2014 新增的多响应、目录订阅、语音广播通知/应答、TCP 文件直传流程没有形成完整闭环。
8. 现有 SDP 主要面向 2016/2022，未按 2011 UDP 和 2014 TCP 下载规则选择构造方式。

## 4. 总体架构

### 4.1 协议版本模型

在 `pkg/gbs/version.go` 中增加规范版本类型，保留旧的 `2011/2016/2022` 展示兼容：

```go
type GBProtocolVersion string

const (
	GBVersion10 GBProtocolVersion = "1.0"
	GBVersion11 GBProtocolVersion = "1.1"
	GBVersion20 GBProtocolVersion = "2.0"
	GBVersion30 GBProtocolVersion = "3.0"
)
```

每个设备保存三个维度：

- `DeclaredVersion`：设备最近声明的 `X-GB-Ver`；
- `EffectiveVersion`：实际下行使用的协议版本；
- `VersionSource`：`header`、`manual`、`default` 或 `inferred`。

设备不携带版本头时不覆盖既有版本；首次遇到未知设备时使用可配置的保守默认值，默认建议 `1.0`。

### 4.2 能力矩阵

增加 `GBCapabilities`，业务判断能力而不是比较年份：

```go
type GBCapabilities struct {
	SupportsConfigQuery       bool
	SupportsCatalogExtension  bool
	SupportsDirectoryNotify   bool
	SupportsMultiResponse     bool
	SupportsMediaStatus       bool
	SupportsVoiceBroadcast    bool
	SupportsVoiceIntercom     bool
	SupportsRTPOverTCP        bool
	SupportsDirectTCPDownload bool
	SupportsH265               bool
	SupportsSnapshot           bool
	SupportsUpgrade            bool
}
```

建议初始能力映射：

| 能力 | 1.0 | 1.1 | 2.0 | 3.0 |
|---|---:|---:|---:|---:|
| RTP/RTCP over UDP | 是 | 是 | 是 | 是 |
| 设备配置查询 | 否 | 是 | 是 | 是 |
| 设备配置写入 | 否 | Basic/视频/音频/SVAC | Basic/SVAC | Basic/SVAC/2022 扩展 |
| 扩展目录字段 | 否 | 是 | 是 | 是 |
| 基础事件订阅/目录通知 | 是 | 是 | 是 | 是 |
| 目录/录像多响应 | 否（接收端兼容厂商分包） | 是 | 是 | 是 |
| MediaStatus/121 | 是 | 是 | 是 | 是 |
| 语音广播 | 否 | 是 | 是 | 是 |

实际产品可通过设备手动覆盖和厂商兼容表修正能力。

### 4.3 版本协商

注册流程改为：

1. 解析设备 REGISTER 中的 `X-GB-Ver`；
2. 平台返回支持的最高版本，或返回协商后的有效版本；
3. 401、403、404、200 等注册响应都按协议要求携带版本头；
4. 记录设备版本来源和最终能力；
5. 后续所有 MESSAGE、NOTIFY、SUBSCRIBE、INVITE、INFO 使用同一份有效档案。

未声明版本的老设备：

- 允许通过管理端指定 `1.0` 或 `1.1`；
- 未指定时采用 `1.0 + UDP` 保守策略；
- 收到明确版本头后更新有效档案；
- 不因一次无版本心跳清空已有版本。

## 9. 发布策略

1. 第一个版本只开放 1.0/1.1 注册、目录、心跳和 UDP 实时点播。
2. 通过设备级开关逐步开放配置、订阅、语音和 TCP 下载。
3. 对 1.1 设备默认关闭 2.0/3.0 专属命令。
4. 日志中输出 `declared_version`、`effective_version`、`capability` 和失败命令。
5. 保留旧 API 和旧 JSON 字段，新增字段使用可选方式，不做破坏性数据库迁移。

## 10. 风险和应对

| 风险 | 应对 |
|---|---|
| 老设备不发送 `X-GB-Ver` | 手动版本覆盖、保守默认、厂商型号兼容表 |
| 设备声称 1.1 但只实现部分能力 | 能力按功能单独探测和关闭，不只信任版本号 |
| 2014 TCP 下载与 2016 RTP over TCP 混淆 | 两套独立 SDP/媒体流程，禁止复用同一个开关 |
| 目录扩展字段造成数据库兼容问题 | 先保存结构化字段和原始 XML，扩展字段采用 JSON 可选存储 |
| 现有 2016/2022 回归 | 四版本 golden 报文 + 原有设备回归矩阵 |
| 设备厂商私有 XML/编码差异 | XML 宽松解析、原始报文落盘、按厂商配置覆盖 |

## 11. 最终建议

继续在当前项目内实现，不独立复制项目。代码组织采用“公共协议核心 + 版本档案 + 能力矩阵 + 少量版本专用构造器”的方式。

范围边界：本方案的“2014 附录 O 裸 TCP 下载”现同时覆盖 Owl 与 2014 设备之间的直连落盘，以及 2014 上级平台以 `m=video ... tcp` 请求、Owl 再向下级设备建立下载并流式转发原始 PS 的级联中继。附录 O 消息 1/2/5 是 SIP 服务器与独立下载客户端的控制腿；Owl 内置 TCP 下载客户端后以进程内调用替代该腿，不生成无意义的自呼 SIP 会话。Owl 发给媒体发送方以及级联入口承接的是规范消息 3，必须携带接收端 `s=Download` SDP。级联能力仅对 2014 `Download` 开放，独立实现上下游 INVITE/ACK/BYE、监听地址宣告、上级来源授权、裸 TCP 字节转发、EOF/MediaStatus/超时终态和会话清理，并与直连下载共享地址、大小和并发限制；默认关闭且不落盘。活动 TCP 字节流不做跨进程续传，进程重启后由上级重新发起下载；真实设备、真实上级、NAT/防火墙和大文件背压仍属于生产互通范围。

附录 G 的持久化在途交换已绑定本平台 ID、外部系统 ID/角色/版本/地址/来源 CIDR、鉴权密码、有效 Date + Note seed、传输和 TLS 档案的 SHA-256 指纹。外部系统删除或任一档案变化后，重启恢复会丢弃旧关联，避免把旧业务发送到新身份；持久层只保存摘要，不保存指纹载荷中的明文秘密。

第一开发阶段不应先实现所有 2014 新功能，优先修复 `X-GB-Ver 1.1`、注册响应和未知版本默认策略。完成版本协商后，再按 2011 基础能力、2014 补充能力、设备联调三个里程碑推进。

管理端同步要求：通道详情“国标扩展”页提供 A.2.4 `Alarm` 主动查询，支持四版本报警级别、方式、时间筛选；`AlarmType` 仅对 2016/2022 开放，并与协议层的版本校验、级联转发保持一致。
