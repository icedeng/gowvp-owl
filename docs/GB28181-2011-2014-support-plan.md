# GB/T 28181-2011/2014 支持开发方案

配套执行文档：[AI 开发执行计划](GB28181-2011-2014-ai-development-plan.md)。

## 1. 目标

在现有 GoWVP Owl 项目中，补齐以下两个协议档案：

| 协议档案 | SIP `X-GB-Ver` | 说明 |
|---|---:|---|
| GB/T 28181-2011 | `1.0` | 基础标准 |
| GB/T 28181-2011 修改补充文件（2014） | `1.1` | 2011 版修改补充文件，不是独立的 GB/T 28181-2014 国家标准 |

现有 2016/2022 能力继续保持兼容。实现目标不是复制一套旧代码，而是在同一套 SIP、事务、设备、媒体和业务模型上增加协议档案和能力分派。

## 2. 依据和范围

依据文件：

- [GBT-28181-2011.pdf](GBT-28181-2011.pdf)
- [GBT-28181-2014.pdf](GBT-28181-2014.pdf)
- [GBT-28181-2016.pdf](GBT-28181-2016.pdf)
- [GBT-28181-2022.pdf](GBT-28181-2022.pdf)

2022 版附录 I 给出的版本对应关系为：`1.0=2011`、`1.1=2011 修改补充文件`、`2.0=2016`、`3.0=2022`。版本号应作为协议协商标识使用，不应直接当作普通年份排序。

本方案覆盖：

1. 设备注册、注销、Digest 鉴权和版本协商；
2. 心跳、设备信息、目录、报警、状态和订阅通知；
3. 实时点播、录像检索、回放和下载；
4. PTZ、语音广播、设备配置及 2014 补充命令；
5. SIP/SDP/XML 报文兼容和多厂商互通测试。

本方案暂不承诺数字证书双向认证、S/MIME 全量实现、所有厂商私有扩展和正式检测认证；这些应作为后续专项。

### 2.1 关键假设

- 原第一阶段以“平台作为 SIP 服务端接入下级 IPC/NVR/网关”为目标；后续工作包已经加入本平台向上级注册、目录共享、媒体转发和标准事件订阅。
- 现有媒体服务器继续承担 RTP 端口分配、PS/音频流接收、语音 RTP 发送和流生命周期管理。
- 开发期间至少能获得两种 1.0 设备和两种 1.1 设备或等价设备模拟器。
- 级联工作包已进入实现：支持四版本注册、目录共享、直播、回放/下载以及 Catalog/Alarm/MobilePosition/PTZPosition 订阅；2022 注册支持 301/302 重定向；Catalog 查询/订阅支持平台根和单个共享通道，按 2011 `Response`、2014+ `Notify` 根发送 ADD/DEL/ON/OFF/UPDATE 增量；上级事件订阅会自动建立、续订、复用和取消真实下级订阅，真实平台互通和生产验收仍需单独排期。

### 2.2 当前实现状态（2026-08-25）

- `1.0/1.1/2.0/3.0` 共用同一套版本协商、能力门禁、SIP/XML/SDP 和设备模型；不需要拆分独立项目。
- 2011/2014 代码能力已完成自动化和本地模拟器覆盖，但真实设备矩阵、目标环境灰度和正式检测认证仍未完成。
- 2014 语音广播按附录 Q 实现“接收者主动 INVITE”，使用 ZLMediaKit 中已就绪的 G.711 A-law 音频流作为语音发送者；`1.1` 使用 `PT 96/PS/90000`，`2.0/3.0` 使用 `PT 8/PCMA/8000`。
- 2016/2022 语音对讲在设备音频流建立后复用同一 RTP 连接反向发送 G.711 A-law 音频；LALMAX 当前不提供 RTP 发送接口，语音发送功能明确返回不支持。
- 上下级平台级联仍按独立验收工作包管理，但代码已在同一项目内实现，不另起项目。
- 2014 广播需要的接收者主动 `INVITE` 已实现；已注册上级的通用入向 `INVITE` 进入级联 B2BUA，未知来源仍明确返回 `501`。
- Alarm 订阅已支持级别、方式、类型和时间过滤；`AlarmType` 按 2016/2022 门禁，2011 附录 J 示例的 `StartTime/EndTime` 作为兼容别名接收。
- NVR 代表已知子通道返回 `DeviceInfo` 时更新子通道元数据，不再因 SIP From 为父设备而误拒绝，也不会覆盖父设备信息。
- 支持通过设备编辑接口的 `gb_disabled_capabilities` 单独关闭固件未实现的扩展能力；运行时门禁、设备能力快照和诊断接口均使用过滤后的有效能力集。

## 3. 当前实现基线和主要缺口

### 3.1 已有基础

- `pkg/gbs/sip` 已具备 SIP 消息、事务、UDP/TCP 监听、Digest 鉴权和 XML 编解码能力。
- `pkg/gbs` 已有注册、心跳、目录、设备信息、报警、录像、PTZ、语音、订阅和 INVITE 基础流程。
- 设备扩展数据已有 `GBVersion` 字段，数据库使用 JSON 扩展，不需要新增独立表。
- 2016/2022 已有部分版本门禁和 `X-GB-Ver` 下行发送逻辑。

### 3.2 必须先修复的问题

1. `pkg/gbs/sip/context.go` 只识别 `1.0/2.0/3.0`，缺少 `1.1`。
2. `pkg/gbs/catalog.go` 的 `wrapRequest` 没有 `1.1` 分支，未知版本默认发送 `3.0`，对老设备不安全。
3. 注册 `401`、`200` 和失败响应没有统一返回 `X-GB-Ver`。
4. 设备不携带版本头时，数据库版本可能被空值覆盖；内存默认版本和下行默认版本不一致。
5. 注册成功后无条件发送 `ConfigDownload`，纯 2011 设备可能不支持。
6. 目录模型缺失 2014 增加的 `ParentID`、`BusinessGroupID`、`IPAddress`、位置属性等字段。
7. 2014 的 `MediaStatus`、多响应、目录订阅、语音广播通知/应答、TCP 文件直传流程没有形成完整闭环。
8. 现有 SDP 主要面向 2016/2022，未按 2011 UDP 和 2014 TCP 下载规则选择构造方式。

## 4. 总体架构

### 4.1 协议版本模型

在 `pkg/gbs/version.go` 中增加规范版本类型，保留旧的 `2011/2016/2022` 展示兼容：

```go
type GBProtocolVersion string

const (
	GBVersion10 GBProtocolVersion = "1.0"
	GBVersion11 GBProtocolVersion = "1.1"
	GBVersion20 GBProtocolVersion = "2.0"
	GBVersion30 GBProtocolVersion = "3.0"
)
```

每个设备保存三个维度：

- `DeclaredVersion`：设备最近声明的 `X-GB-Ver`；
- `EffectiveVersion`：实际下行使用的协议版本；
- `VersionSource`：`header`、`manual`、`default` 或 `inferred`。

设备不携带版本头时不覆盖既有版本；首次遇到未知设备时使用可配置的保守默认值，默认建议 `1.0`。

### 4.2 能力矩阵

增加 `GBCapabilities`，业务判断能力而不是比较年份：

```go
type GBCapabilities struct {
	SupportsConfigQuery       bool
	SupportsCatalogExtension  bool
	SupportsDirectoryNotify   bool
	SupportsMultiResponse     bool
	SupportsMediaStatus       bool
	SupportsVoiceBroadcast    bool
	SupportsVoiceIntercom     bool
	SupportsRTPOverTCP        bool
	SupportsDirectTCPDownload bool
	SupportsH265               bool
	SupportsSnapshot           bool
	SupportsUpgrade            bool
}
```

建议初始能力映射：

| 能力 | 1.0 | 1.1 | 2.0 | 3.0 |
|---|---:|---:|---:|---:|
| RTP/RTCP over UDP | 是 | 是 | 是 | 是 |
| 设备配置查询 | 否 | 是 | 是 | 是 |
| 扩展目录字段 | 否 | 是 | 是 | 是 |
| 基础事件订阅/目录通知 | 是 | 是 | 是 | 是 |
| 多响应 | 否 | 是 | 是 | 是 |
| MediaStatus/121 | 是 | 是 | 是 | 是 |
| 语音广播 | 否 | 是 | 是 | 是 |
| 语音对讲 | 否 | 否 | 是 | 是 |
| RTP over TCP | 否 | 否（另有 TCP 下载规则） | 是 | 是 |
| 2014 直接 TCP 文件下载 | 否 | 是 | 厂商兼容扩展 | 厂商兼容扩展 |
| PTZ 精准位置变化订阅/通知 | 否 | 否 | 否 | 是 |
| 巡航轨迹列表/详情查询 | 否 | 否 | 否 | 是 |
| H.265/AAC、升级、抓拍 | 否 | 否 | 否 | 是 |

实际产品可通过设备手动覆盖和厂商兼容表修正能力。

### 4.3 版本协商

注册流程改为：

1. 解析设备 REGISTER 中的 `X-GB-Ver`；
2. 平台返回支持的最高版本，或返回协商后的有效版本；
3. 401、403、404、200 等注册响应都按协议要求携带版本头；
4. 记录设备版本来源和最终能力；
5. 后续所有 MESSAGE、NOTIFY、SUBSCRIBE、INVITE、INFO 使用同一份有效档案。

未声明版本的老设备：

- 允许通过管理端指定 `1.0` 或 `1.1`；
- 未指定时采用 `1.0 + UDP` 保守策略；
- 收到明确版本头后更新有效档案；
- 不因一次无版本心跳清空已有版本。

## 7. 里程碑和验收标准

### M0：协议档案和测试基线

预计 2～3 人日。

验收：四个版本可解析，版本映射测试通过，报文夹具目录建立。

### M1：版本协商和注册兼容

预计 3～5 人日。

验收：1.0/1.1/2.0/3.0 注册流程均可完成，401 和 200 响应包含正确版本头，未知设备不会默认发送 3.0。

### M2：2011 基础能力

预计 6～10 人日。

验收：至少两个 2011 设备完成注册、心跳、目录、UDP 实时点播、PTZ、录像查询和报警。

### M3：2014 补充能力

预计 10～16 人日。

验收：1.1 设备完成目录扩展、配置查询、目录订阅、多响应、媒体结束通知、接收者主动 INVITE 的语音广播和 TCP 下载；广播必须核对实际音频 RTP，而非只检查 SIP 200。

### M4：回归和灰度发布

预计 6～10 人日，设备厂商等待时间另计。

验收：2016/2022 现有能力无回归；语音对讲同时验证设备上行音频和平台下行 G.711 音频；每个设备可查看有效版本、能力和最近错误；可按设备关闭某个扩展能力。

## 9. 发布策略

1. 第一个版本只开放 1.0/1.1 注册、目录、心跳和 UDP 实时点播。
2. 通过设备级开关逐步开放配置、订阅、语音和 TCP 下载。
3. 对 1.1 设备默认关闭 2.0/3.0 专属命令。
4. 日志中输出 `declared_version`、`effective_version`、`capability` 和失败命令。
5. 保留旧 API 和旧 JSON 字段，新增字段使用可选方式，不做破坏性数据库迁移。

## 10. 风险和应对

| 风险 | 应对 |
|---|---|
| 老设备不发送 `X-GB-Ver` | 手动版本覆盖、保守默认、厂商型号兼容表 |
| 设备声称 1.1 但只实现部分能力 | 能力按功能单独探测和关闭，不只信任版本号 |
| 2014 TCP 下载与 2016 RTP over TCP 混淆 | 两套独立 SDP/媒体流程，禁止复用同一个开关 |
| 目录扩展字段造成数据库兼容问题 | 先保存结构化字段和原始 XML，扩展字段采用 JSON 可选存储 |
| 现有 2016/2022 回归 | 四版本 golden 报文 + 原有设备回归矩阵 |
| 设备厂商私有 XML/编码差异 | XML 宽松解析、原始报文落盘、按厂商配置覆盖 |

## 11. 最终建议

继续在当前项目内实现，不独立复制项目。代码组织采用“公共协议核心 + 版本档案 + 能力矩阵 + 少量版本专用构造器”的方式。

第一开发阶段不应先实现所有 2014 新功能，优先修复 `X-GB-Ver 1.1`、注册响应和未知版本默认策略。完成版本协商后，再按 2011 基础能力、2014 补充能力、设备联调三个里程碑推进。
