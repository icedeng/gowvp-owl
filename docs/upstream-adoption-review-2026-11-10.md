## 3. 建议吸纳的 7 项

### A1. 媒体播放代理权限边界：优先隔离管理能力，播放限制按发布策略适配

上游来源：[6f6edd43](https://github.com/gowvp/owl/commit/6f6edd43)，增强代理权限控制。

**当前问题与调用链**

`setupRouter → /proxy/sms/*path → proxySMS → verifyPlayToken → 节点解析 → ReverseProxy`，集中于 [api.go](../internal/web/api/api.go)。

现有 [ipc.go](../internal/web/api/ipc.go) 的 `play` 生成含 app、stream、media_server_id 的 42 小时播放 token；两个媒体驱动把 token 写入 HTTP/WS-FLV、HLS、WebRTC 地址，RTSP/RTMP 返回直连地址。页面允许复制这些地址。这条链不要求持链接的第三方播放器具有管理端登录态；上述 42 小时只描述本次检查到的该播放接口，不代表所有媒体地址统一期限。

- `verifyPlayToken` 对普通路径使用 `strings.Contains(path, stream)`，没有严格约束 app 和完整 stream。流名前缀/子串相同或同名跨 app 的路径可能误通过。
- WebRTC 查询参数 app/stream 的放行分支没有限定只能访问 `/index/api/webrtc`，也没有限定 `type=play`；合法播放凭据可能被用于代理其他媒体服务 API，实际后果还取决于媒体服务自身鉴权。
- `.mp4/.m4s/.ts` 后缀在没有 token 时直接豁免，未执行播放凭据及节点绑定校验。若目标是受控或到期撤销的播放，该分支破坏相应边界；若资源按约定公开供第三方及缓存读取，无 token 分片本身不足以认定为漏洞。实际发布范围尚未逐路核实，不能统一取消豁免。
- 当前 `proxySMS` 没有独立的播放路径白名单。

**吸纳方式**

优先借鉴播放入口与管理能力隔离；精确资源校验用于已有受控播放。HLS 子资源凭据传递只在对应发布策略要求时适配，不能把整套上游授权政策直接用于全部外部播放。不要覆盖整个 `api.go`。

必须同时完成：

1. 先按现有路由规则解析并校验媒体节点，再对剥离节点前缀后的媒体路径做规范化和白名单检查。不能把合法 `/proxy/sms/<节点路由>/...` 当作上游单节点路径处理。
2. 仅开放现有驱动实际支持的播放路径与 HTTP 方法。WebRTC 只允许明确的播放信令端点和 `type=play`，不能由 app/stream 查询参数放行管理端点。
3. 对限定到具体资源的播放凭据，app 与 stream 按完整路径段、已知 FLV 文件后缀匹配。上游 `stream + "."` 的泛前缀判断也需收紧，避免带点的不同流名仍碰撞；同时兼容 ZLM 与 Lalmax 的不同路径结构。已经明确公开的资源继续按其发布约定提供。
4. 先核实第三方使用的协议、公开范围、CDN/缓存、已有链接与撤销约定。如果决定某类 HLS 分片必须鉴权，清单重写与收紧入口必须同一补丁交付，覆盖普通分片、子清单，以及 `EXT-X-MAP`、`EXT-X-KEY` 等标签中的 URI；保留合法原查询参数和节点路径，拒绝把凭据写入外域 URL。不能把取消全部免鉴权作为无条件前提。
5. 保留现有 JWT 签名密钥、有效期、`media_server_id`、停用节点拒绝、默认节点兼容和 RTMP session 查询参数。旧版合法 token 的兼容限于原有默认节点，不允许成为跨节点通行证。
6. 保持 `/openmedia` 的票据、Scope 和撤权规则独立，不替换为管理端 playToken；第三方也可按现有约定继续使用旧播放地址或 RTSP/RTMP。开放平台文档中“只开放新入口”的网络隔离要求用于声明应用级资源授权闭环，不自动成为全平台禁止旧链接的部署要求。

**不能直接复制上游的原因**

上游 `rewriteM3U8WithToken` 跳过所有 `#` 开头的行，因此不会给 `#EXT-X-MAP:URI="init.mp4"` 增加 token。我们 ZLM 驱动启用了 HLS fMP4；若照搬后取消所有分片免鉴权，初始化片段会被拒绝，可能黑屏。

我们自己的 [openapi/media.go](../internal/web/openapi/media.go) 中 `rewriteHLS` 已处理标签 URI 和普通资源行，可复用其解析思路或抽取最小纯函数。不能直接复用其业务 URL 拼接：开放平台使用 ticket 和会话路径，与管理端不同。上游读取清单无大小限制、直接拼接 token 的实现也不应原样引入。

**必要检查**

第三方播放器不登录管理端即可继续使用约定的播放地址；默认节点/非默认节点的 FLV、HLS fMP4（清单、init、分片）、WebRTC 和既有 RTSP/RTMP 接入保持兼容。管理 API 不经播放入口提供；限定到资源的凭据不能访问其范围外的 app/stream/节点。公开资源与受控资源按各自策略检查，不能统一断言所有无 token 分片必须拒绝。合法 RTMP session 与开放平台播放保持原行为。重点复用 [proxy_sms_test.go](../internal/web/api/proxy_sms_test.go)，补足第三方接入、多节点与 HLS 标签边界。

预期影响：隔离播放与管理能力，按已有发布约定处理资源访问；保留第三方合法播放与接口响应结构。匿名分片是否调整取决于业务发布策略，不能直接归为“必须修复”。本轮没有实施这些变化。

### A2. 公钥接口限流：优先

上游来源：[d773c574](https://github.com/gowvp/owl/commit/d773c574)，以及 [518eaab4](https://github.com/gowvp/owl/commit/518eaab4) 的相关接线。

**当前证据**：[user.go](../internal/web/api/user.go) 的 `RegisterUser` 直接注册 `/login/key`，未接入路由限流。`getPublicKey` 除返回公钥，还生成 HTTP 登录使用的随机 `oaep_seed`。[auth.ts](../admin-ui/src/services/auth.ts) 的登录和修改密码都会先请求该接口。

**需要吸收**：使用令牌桶控制突发与持续请求，沿用现有 `golang.org/x/time/rate` 依赖，不为此升级 goddd。拒绝时返回项目格式的 HTTP 429，提供可理解的重试提示。

**保护约束**：

- 保留响应的 `key` 和 `oaep_seed`，不能替换为上游仅返回 `key` 的实现。
- 限流覆盖成本入口但允许正常多标签页登录、密码修改和合理重试；上游“全局容量 20、每 10 秒补 1”的数值只能作为参考，不能未经容量评估直接固化。
- 若采用客户端维度限制，必须限定代理可信来源、设置状态容量/过期回收；不能直接相信任意 `X-Forwarded-For`，也不能按外部输入无限建桶。全局上限与客户端限流应协调，避免一个来源耗尽额度后阻断所有合法用户。
- 前端遇到 429 不清理已有会话、不跳转循环，继续使用现有错误展示；需要时局部补重试时间提示。

**必要检查**：HTTP fallback 与 HTTPS 登录、已有会话下修改密码、多次正常请求继续成功；超限得到 429，恢复后可重试，返回字段不变。优先复用 [user_test.go](../internal/web/api/user_test.go)。

### A3. 登录失败防护：优先，但不能照搬账号全局锁定

上游来源：[518eaab4](https://github.com/gowvp/owl/commit/518eaab4)。

**当前证据**：`POST /login` 未接限流或失败退避；`login` 执行解密和凭据比较。仅限制公钥接口不能阻止持有公钥的客户端持续提交密码尝试。

**上游实现的副作用**：一个 `loginGuard` 共享整个管理员账号的失败状态，持互斥锁执行 `c.Next()`；全部非 2xx 结果都会计数。首次 5 次失败后锁定 1 分钟，后续失败依次扩大到 5 分钟、1 小时、8 小时。这样未认证请求可锁住所有管理员，解密/绑定异常也会被算作密码错误，不符合本项目的兼容目标。

**需要吸收**：在解密前限制请求速率与大小，在凭据核验后对失败做受控退避；把“凭据错误”与“输入非法、密钥过期、服务故障”分开记录。采用有容量与到期回收的来源防护，配合适度全局上限；不引入单个匿名来源可触发的长期账号全局锁定。锁只保护防护状态，不应跨整个请求处理持有。

**保护约束**：保留 `credentialsMu`、`SaveAdminCredentials`、旧密码校验、HTTP 加密兼容、现有账号和 JWT 期限；不引入初始化向导、默认密码回退或 15 天自动登录。共享 VPN/NAT 出口下的正常管理员也必须纳入阈值设计。

**必要检查**：错误凭据受限；并发请求不能绕过约束；合法来源仍可登录；服务错误/公钥轮换不触发长期账号锁定；密码修改、重启后的凭据恢复保持原行为。复用 `user_test.go`，只增加与防护行为直接相关的回归用例。

### A4. 录像清理零进展退出加速循环：优先

上游来源：[231f3970](https://github.com/gowvp/owl/commit/231f3970)。

**当前证据**：[cleanup.go](../internal/core/recording/cleanup.go) 中 `StartCleanupWorker → runCleanup → cleanupByDiskUsage`。`cleanupByDiskUsage` 最后只根据磁盘使用率返回是否继续；没有录像可删、文件删除一直失败或其他程序占满磁盘时，仍可能每 2 分钟清理并推送告警。单次最多 20 批，不代表外层循环会停止。

**需要吸收**：区分“磁盘仍超标”和“本轮有推进”。没有可删目标或没有推进时退出加速循环，回到现有 10 分钟常规检查；仍保留超标告警。实际删除记录/清理已不存在文件对应的记录也算推进，不能只看释放字节数。

**必须适配的细节**：上游退出条件包含 `failedCount == 0`，因此持续删除失败时仍可能密集重试。我们应根据实际推进判断，而不是把失败次数当作进展；失败要保留原因与后续恢复机会。

**保护约束**：保持现有保留天数、最旧录像优先、每批数量、删除成功或文件已不存在后才删数据库记录、路径边界校验与 ctx 取消。不引入 `cleanupDiskByFilesystem`、`scanDateDirs` 或按目录 `RemoveAll`，不增加任何新的可删除文件。

**必要检查**：无录像但超标、全部删除失败时停止加速；常规周期仍执行；有推进且仍超标时按策略继续；磁盘达标/取消能退出；原有过期与按空间删除规则不变。现有该包没有上游新增的 `cleanup_test.go`，实施时值得为这几个稳定边界补小范围回归。

### A5. SIP 响应队列满时避免阻塞消息分发：优先，单独交付

上游来源：[7b6f1f15](https://github.com/gowvp/owl/commit/7b6f1f15)。

**当前证据**：[sip/server.go](../pkg/gbs/sip/server.go) 的 `handlerListen → handlerResponse → receiveResponse` 同步处理响应；[sip/tx.go](../pkg/gbs/sip/tx.go) 的响应队列容量为 10，最终入队使用 `select { case <-tx.done; case tx.resp <- msg }`，没有队列满的非阻塞分支。

这比永久阻塞已有改善：事务结束会解除等待，1xx 不占队列，部分 INVITE 重传/分叉已有专门处理。但未消费的其他最终响应仍可能填满队列，让该消息分发循环等待，影响同一循环后续消息。该结论来自控制流，尚未执行复现。

**需要吸收**：最终响应队列饱和时快速结束本次分发，并记录受控日志/计数；不能为了避免阻塞而关闭一个仍合法存活的事务。

**保护约束**：

- 改动限于最终交付队列的过载策略；在队列判断前保留信令摘要校验、INVITE 非 2xx ACK、2xx ACK 重传、分叉、取消后迟到响应等处理。
- 明确重复响应与首个合法最终响应的取舍。不能随意覆盖队头，也不能让无关响应占满队列导致正确结果丢失。
- 保留现有 `done`、`closeOnce`、`watchDone`、事务 owner、后台任务收尾、连接释放及服务端重传窗口；不得连带移植上游“handler 返回立即 tx.Close”。
- 不改国标业务会话、SDP、级联、历史回放和下载 API。

**必要检查**：满队列时消息分发迅速返回，其他事务继续处理；正常最终响应可获得；ACK/重传、取消后迟到 2xx、分叉、事务关闭/连接释放仍保持原行为。优先复用 [tx_lifecycle_test.go](../pkg/gbs/sip/tx_lifecycle_test.go)，涉及并发边界时执行该范围竞态检查。

### A6. 监控采集改为间隔差分：后续小优化

上游来源：[8a943304](https://github.com/gowvp/owl/commit/8a943304)，仅吸收统计采集部分。

**当前证据**：[stat.go](../plugin/stat/stat.go) 的 `LoadTop` 每轮读取两次网卡计数，中间阻塞 1 秒，随后重置 ticker 为 200ms。现有唯一调用方在 `setupRouter`，传入回调只丢弃参数，但采集器仍构造 map。不能把当前实现描述成每秒采集 20 次：中间的阻塞实际限制了频率。

**需要吸收**：按约 1 秒周期采集，用前后计数及真实 elapsed 计算 bps，移除无意义回调/map 分配；只改采集器和唯一调用点。

**保护约束**：保留 30 点环形队列、时间字段、JSON 字段与网络单位；首个样本不伪造速率；计数器回退/网卡变化不能 uint64 下溢产生巨值。当前统计值的并发访问仍需按影响范围检查，不能把此优化当成已解决所有竞态。

**必要检查**：核对静态调用关系及网络单位；若调整计算，验证真实采样间隔和计数器回退。保留 `/app/metrics/api` 的 `goroutines` 历史数据和 `goroutine_count` 当前值，不能用上游单个整数覆盖现有字段结构。不为此升级依赖。

### A7. `/web` 规范重定向：后续低风险修复

上游来源：[b05d8386](https://github.com/gowvp/owl/commit/b05d8386)。

**当前证据**：[api.go](../internal/web/api/api.go) 注册 `/web/` 静态资源和 NoRoute 回退，没有显式 `/web` 路由；[vite.config.ts](../admin-ui/vite.config.ts) 的 `base` 为 `./`。无尾斜杠直接返回 HTML 时，相对资源可能按站点根目录解析。

**需要吸收**：仅将精确 `/web` 规范到 `/web/`，保留查询参数，并核对前端 hash 路由的目标保留。不能宽泛重定向 `/webhook` 或修改 API、静态目录、构建资源路径。

**必要检查**：HTTP 层核对 `/web` 的重定向及 `/web/` 正常资源路由；登录跳转参数继续有效。此项不需要改数据库和前端构建链路。

## 4. 两项按需引入，本轮不默认启用

### B1. 独立 ONVIF 凭据

来源：[af992002](https://github.com/gowvp/owl/commit/af992002)。

[onvifserver/register.go](../internal/web/onvifserver/register.go) 当前把 `cfg.Server.Username/Password` 传入 SOAP 服务，服务在注册路由时创建；ONVIF 与后台账号耦合，修改后台密码后运行中的 SOAP 凭据也未通过这条路径同步重建。

值得吸收独立配置和一致的凭据读取方式，但**不能直接引入上游首次启动随机生成独立密码**，否则现有 NVR/HA 等客户端会认证失败。

若实施：旧部署缺少 ONVIF 配置时，先以一次性迁移保留当前实际使用的 ONVIF 凭据；新安装生成独立凭据；保存成功后才切换；提供明确的后续轮换步骤。迁移前需核对正在运行的 SOAP 凭据是否与最新管理员配置一致，不能只据磁盘当前值推断。凭据迁移应避免环境变量密钥被无意写回普通配置。之后修改后台密码不得联动改变 ONVIF。ONVIF URI、发现地址、Profile、媒体节点选择及网页登录均保持原行为。

是否纳入取决于实际 ONVIF 对外使用情况，必须作为独立迁移任务。

### B2. H.265 WebRTC 按需转码预览

来源：[f0714688](https://github.com/gowvp/owl/commit/f0714688)、[1589a009](https://github.com/gowvp/owl/commit/1589a009)、[d1dd3352](https://github.com/gowvp/owl/commit/d1dd3352)，需要一起理解。

上游新增 FFmpeg 子进程、共享转码任务、并发与空闲回收、输出码率限制、`owl_preview` 内部 app，以及保留历史同名通道/播放 session 的兼容处理。这是新增能力，不是当前必须纳入的稳定性补丁。

若存在明确 H.265 浏览器播放问题，可借鉴“原流保留，单独为观众生成 H.264 预览”的结构；首次接入默认关闭。必须验证镜像内 FFmpeg/编码器、CPU 容量、跨节点键、停用节点、原通道权限、session 参数和无人观看回收，原始录像、AI、抓拍及级联继续使用原流。历史 `owl_preview` 通道不得自动改名或接管；冲突时保持旧业务并禁用新能力。

上游当前代理仍按全局媒体快照接线，不能认定新建 job 带 serverID 就已兼容我们的多节点路由。开放平台首期只开放既有 HLS/FLV，不能随预览移植扩大协议权限。

### 8.2 登录防护参数与预期影响

沿用现有 `golang.org/x/time/rate`，每个服务实例、每个路由类别分别限流：

| 入口 | 每来源持续速率 / 突发容量 | 全局持续速率 / 突发容量 |
| --- | --- | --- |
| POST `/login` | 1 次/秒，容量 20 | 20 次/秒，容量 100 |
| GET `/login/key` | 2 次/秒，容量 30 | 20 次/秒，容量 100 |

这些是本轮采用的本地默认值，依据正常页面登录和修改密码的一次公钥请求、一笔密文提交留出多标签与重试余量；没有进行线上容量压测。来源已被拒绝的请求不继续消耗全局令牌。来源状态最多 4096 项，闲置 15 分钟后在请求触发的周期回收中清除，容量满时替换最久未访问来源。全局上限仍可能在多来源洪泛时短暂影响合法请求，不声称消除所有拒绝服务风险。

仅明确的账号密码错误计入失败次数，第 5 次开始退避 1 秒，后续逐次加倍至最多 30 秒；限流拒绝不延长退避，成功凭据校验重置失败状态。解密、绑定、服务配置或生成 JWT 错误不计为密码失败，不持防护互斥锁执行请求。不设账号全局锁。

`/login` 在绑定和解密前限制请求体为 4 KiB，现有 2048 位 RSA 密文封装远小于该限制；过大返回 413。限流返回包含中文 `msg` 的 429 和 `Retry-After`。前端既有处理只在 401 时清会话，429 保持会话并显示服务端提示，本轮不修改前端。

**来源识别边界**：只读取 `RemoteAddr` 的 TCP 对端，不采信未配置可信代理的 `X-Forwarded-For` 或 `X-Real-IP`，也不更改全局 Gin/开放平台的代理配置。共享 NAT/VPN 或反向代理下多个管理员可能共用一个来源桶及最多 30 秒失败退避。未核实线上管理入口的代理拓扑；若要求在代理后按真实终端隔离，需先确认可信代理网段，再决定单独扩展登录入口的来源解析，不能直接信任外部转发头。

### 8.5 过期录像与事件清理失败循环修复

本次修改限于两条批量清理循环、对应回归测试及本文档。保留原有过期判定、保留天数、100 条批次、常规调度周期、录像路径和符号链接保护、空目录清理、事件图片先删再删数据库记录的顺序。未修改登录、媒体代理、SIP、监控、依赖或数据库结构。

- **过期录像**：[cleanup.go](../internal/core/recording/cleanup.go) 的 `batchDeleteRecordings` 依据事务成功后的实际删除行数判断进展。文件路径无效、全部文件删除失败、数据库删除失败或删除返回零行时，统计本批结果后退出，不重复查询首批失败记录。文件已不存在时仍允许清理对应数据库记录；部分失败但仍有成功删除时继续处理下一批，最终仅剩失败记录时退出。已删除文件但数据库失败的记录继续保留，后续按原有缺失文件分支恢复，不新增补偿删除或扩大可删范围。
